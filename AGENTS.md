# Agent guide

## OpenSpec workflow

- Every change is an OpenSpec change under `openspec/changes/<change-name>/` using the `spec-driven` schema. Project context and per-artifact rules live in `openspec/config.yaml`; the CLI feeds them into each artifact's instructions.
- Use the generated workflows: `/opsx:propose`, `/opsx:apply`, `/opsx:archive` in Claude Code, and the matching `openspec-*` skills in Codex. They are generated files; regenerate them with `npx openspec update` instead of editing them.
- Commit order on a change's branch:
  1. proposal, design, spec deltas and tasks (about eight tasks at most);
  2. small implementation commits;
  3. `verification.md`;
  4. `npx openspec archive <change-name>` as the final commit.
- Run `npm run openspec:validate` (strict) before every commit that touches `openspec/`. A failing validation blocks the change.

## One change per pull request

- A branch is named after its change and carries exactly that one change.
- Branch from `master`, or from the predecessor change's branch while its pull request is still open.

## Verification evidence

- Each change has `verification.md` beside its proposal. List the commands you ran and what they printed or produced.
- Keep fixture-tested scope separate from live evidence. When a live dependency is unavailable, list the requirement as unverified; fixture results never stand in for a live run.
- Preserve real failures: record a failed step as a failure with its output, never as a skip, a warning or a success. Report execution failures separately from visual differences.
- Mark a task done only when the evidence it names is recorded.

## Canonical executable

- `bin/ChummerGenSR4.exe` is the canonical build and is immutable. Never rebuild, replace, copy over or edit it.
- The app's Release configuration builds `ChummerGenSR4.exe` into `bin/`, so never build it with the default output path.
- Before and after any run that launches it, record its SHA-256. Both must equal `9ff3009946f0212842eb5aa803c3d8e1697752040229f52b25f584e7b0ae9e56`.

## Contracts

- Data read or written by more than one language is defined by a JSON Schema in `contracts/schemas/`. Edit the schema, then run `npm run contracts:generate`; never edit `contracts/generated/` by hand.
- Every schema needs an example in `contracts/examples/`. `npm run contracts:check` (drift), `npm run contracts:test` (TypeScript round-trip) and `npm run parity:test` (C# round-trip) must pass.

## Visual parity capture

- `npm run build:candidate` builds the app and its class library (`Core/Core.csproj`) from the current source into `out/candidate/bin/`. Use it instead of building `Chummer/Chummer.csproj` yourself.
- `npm run parity` captures every case in `parity/cases/characters.json` on the canonical and the candidate executable in one run; `npm start` runs the parity workflow instead (see below). Pass options after `--`, for example `npm run parity -- --case Diego_v_alpha2_by_bessgeor --capture common`; `--help` lists them. In PowerShell, call `npm.cmd` instead of `npm`, because the `npm.ps1` shim drops the `--`.
- A run writes only under `out/runs/<runId>/`: staged apps, fixture copies, `captures/`, `summary.json`, `results.json`, `coverage.json`, `timing.json` and the comparer's `compare/`. The exit status is 0 (all passed), 1 (visual differences), 2 (execution failures) or 3 (setup error). Read `coverage.json` for execution (`valid`, `invalidReasons`, failures, and optional absences listed apart from them) and `results.json` for visual pass/fail, and report them separately. Invalid coverage alone gives status 2. `timing.json` holds the durations of every UI operation; it measures, it never decides an outcome.
- With `--ui-tree` the candidate side records, after each capture, the UI Automation tree of the captured window as shown (elements not off screen; the automation ID is the WinForms control name) in `ui-trees/<case>/<capture>.json`, and the summary's `uiTrees` names the folder. A tree that cannot be recorded fails its capture action. The canonical side and the canonical cache are unaffected.
- Besides `selectTab`, `waitFor`, `wait` and `capture`, a case can act: `setValue` (`control`, `value`) types into a text box or numeric up-down and leaves it with Tab, `click` (`control`) presses a button or toggles a check box, `selectItem` (`control`, `item`) selects a list, drop-down or tree item, `contextMenu` (`control`, `item`) opens the control's (or its selected tree node's) context menu with the context menu key and invokes an item, and `saveReload` saves with Ctrl+S, closes the app and opens the saved file again. A control is named by its WinForms name. `setValue` and `selectItem` fail when they change nothing. Every action applies to the active window, the main window or the modal dialog it shows; a capture with a dialog open captures the dialog. No action moves the pointer. A case with `saveReload` gets a fixture copy per side. `parity/cases/rich-scenarios.json` holds scenarios that use them; run it with `npm start -- --case-file parity/cases/rich-scenarios.json`.
- Run-specific settings go in a folder passed with `--settings-overlay`. Keep it outside the repository or under `out/`; never edit `bin/settings/` for a run.
- The fixtures use sourcebooks that `bin/settings/default.xml`, which enables only the core book, does not enable; without them the cases that need them fail at startup on both sides. To run the suite, pass an overlay holding `settings/default.xml`: a copy of `bin/settings/default.xml` (UTF-16) with these books added to `<books>`: `AR`, `AT`, `AU`, `DG`, `GH`, `RC`, `RW`, `SA`, `SDN`, `SG`, `SM`, `TOD`, `UCL`, `UN`, `WA` and `WAR`.
- `--canonical-cache <dir>` (outside the repository or under `out/`) reuses the canonical side of a case from an earlier run when every input it is keyed on is the same (the staged canonical app, the fixture, the actions, the screens and their scale, the OS build, the Windows colour and text settings, the app's registry options and the runner's own assemblies), and stores canonical sides that completed. A reused side is marked `cache` in the summary and in `coverage.json`, with the run that stored it; say so when you report a run. Leave the cache off for evidence that must show both executables running.
- Add a fixture to `parity/fixtures/characters/` only after reviewing its content (names, notes, links, images), and declare its mode in the case file.

## Visual parity compare

- `npm run compare -- --run out/runs/<runId>` analyzes a capture run: it reads `results.json` and replaces only `out/runs/<runId>/compare/` with `report.json` and the crops under `crops/`. `--no-ocr` turns OCR off; `--help` lists the options.
- The comparer's exit status is 0 (every row passed), 1 (differences reported), 2 (analysis failures: a row could not be analyzed, OCR failed, or a planned capture is unaccounted) or 3 (setup error, no report). The comparer needs the run's `coverage.json`.
- The report's `completeness` accounts for every planned capture: `reported`, `analysis-failed`, `filtered`, `optional-absent`, `execution-lost` or `unaccounted`. Report its totals with the comparer's outcome. Report the comparer's outcome apart from the capture run's execution outcomes and visual results.
- Discrepancies come only from the raw pixel difference. OCR text helps a reader; it never shows that a difference is gone or that two discrepancies are the same. Duplicates share the same changed pixels at nearly the same place.

## Parity workflow

- `npm start -- <options>` runs the LangGraph graph in `workflow/`: build (the candidate and the parity tools), then capture the cases, one per desktop lane at a time (see Desktop use), with each captured case compared while the next ones are captured, then triage, then the interaction inventory (see below), then discovery when the scope shows no difference (see Interaction discovery) or else diagnosis, repair and widening and next attempts for rejected clusters, then the outcome (see below; `--no-diagnosis` ends the run after triage, `--no-repair` after diagnosis, `--no-widening` after repair, `--no-discovery` concludes a clean scope without discovery; each of them still concludes). Capture options (`--case`, `--capture`, `--settings-overlay`, `--threshold`, `--case-file`) go to the capture runner, `--no-ocr` and `--tessdata <dir>` to the comparer; `--help` lists them. Each case gets its own run folder under `out/runs/`.
- The workflow graph has one node per stage, each a LangGraph subgraph that shares the thread's state: `start` (the build), `capture` (the captures and compares of the planned cases, then triage and the inventory), `discovery` (the thread's discovery thread), `diagnose` (the sealed contexts, hypothesis and challenge jobs, quota waits and the check), `repair` (the attempts and their quota waits), `widen` (the widening, promotion and rollback, one cluster at a time) and `conclude` (the dispositions and `outcome.json`). The stage IDs are exported as `stageIds` from `workflow/src/graph/workflow-graph.ts` and never change; each stage's builder is in `workflow/src/graph/stages/`. The routing between stages, the next attempts back to `repair` and the stages a thread's options leave out are edges of the workflow graph; fan-outs stay inside their stage, so a pending task's arguments are in its stage's checkpoint namespace (`capture:<task id>`, …). `getGraphAsync({ xray: true })` draws every stage with its inner nodes, and `getState(config, { subgraphs: true })` returns the running stage's state and pending tasks.
- Without `--case-file`, a new thread's case file is its suite, `out/workflow/threads/<thread>/suite-cases.json`: the document of `parity/cases/characters.json` followed by the cases of `parity/cases/discovered.json` when the discovery registry exists, with their fixture paths relative to the suite. A registry without its case file or the other way round, a case file that is not the registry's rendering, a discovered file whose startup delay or settle time differs from the fixture file's, or a case name in both files is a setup error before the build. The suite is written once when the thread starts, and a resumed thread keeps it. With `--case-file` the thread uses that file. Capture steps are keyed by the case, not the case file, so steps recorded from `characters.json` are reused from the suite.
- The exit status is the highest capture and compare status of the cases (0, 1 or 2) and the exit status of the thread's discovery (0, 1 or 2), 2 when a diagnosis or repair job failed a cluster or the check capture, a narrow check or a widening capture had execution failures, or 3 for a setup error; the thread's outcome (see Loop) never changes it. Report each case's execution outcome (capture status, coverage, where the canonical side came from) apart from its visual outcome (results, report status and completeness); the workflow prints both for every case at the end of the run, also with `--only`.
- Every run is a thread, checkpointed in `out/workflow/checkpoints.sqlite`; the thread ID is printed at the start. After a crash, Ctrl+C or a setup error, `npm start -- --resume <thread>` continues it with its original options. A resumed stage repeats only its unfinished tasks. A thread checkpointed before the workflow graph had stages cannot be resumed: `--resume` ends with a setup error (3) that says so; start a new thread instead, which reuses the old thread's recorded capture and compare steps.
- Capture and compare steps are keyed by their inputs and recorded under `out/workflow/steps/`. A step with the same inputs and intact outputs is reused, also by a new thread, and is reported as reused with the thread it came from. A capture key covers the machine environment the pixels depend on (screens and scale, OS build, Windows colour and text settings, the app's options); steps with status 2 are never reused, and `--recapture` captures every planned case again even when a step is recorded (a difference that looks like a paint race). `--only capture|compare|triage|diagnose` runs one node; the nodes before it must find recorded steps.
- Capture uses the canonical capture cache by default: `--canonical-cache <dir>`, else `PARITY_CANONICAL_CACHE`, else `canonicalCache` in the local profile, else `%LOCALAPPDATA%\ChummerGenSR4\canonical-cache`. All worktrees share it. Pass `--live-canonical` for evidence that must show the canonical executable running.
- Cache entries are keyed on the capture runner's assemblies, so every checkout must build them byte for byte: the parity and generated C# sources have their line endings pinned to CRLF in `.gitattributes`. Keep them CRLF when you write these files, and do not commit attributes that change it.
- The optional local profile (`PARITY_WORKFLOW_PROFILE` or `%LOCALAPPDATA%\ChummerGenSR4\workflow-profile.json`) may set `canonicalCache`, `settingsOverlay`, `cpuPool`, `agents` (see Diagnosis), `certificates` (see Evaluation), `tuning` (see Tuning), `lanes` (see Desktop use), `discovery.targets` (see Interaction discovery), `diagnosis.hypotheses` (see Diagnosis), `repair.deadlineMinutes` and `repair.tries` (see Repair) and `repair.maxAttempts` (see Loop).
- Triage writes `out/workflow/threads/<thread>/triage.json`: discrepancy clusters across cases (same image hash, core at nearly the same place) with identities that stay the same across runs, and the rows and captures without pixel analysis listed apart.
- `npm run workflow:typecheck` and `npm run workflow:test` check the workflow; CI runs them with the parity build and `contracts:check`.

## Interaction inventory

- The workflow's capture steps record UI trees (`--ui-tree`; check, narrow, level and baseline captures do not), and an `inventory` node follows triage whenever triage runs. It writes `out/workflow/threads/<thread>/inventory/source-inventory.json` and `coverage-manifest.json` and prints an `Inventory:` line after the triage totals; it changes the exit status only by a setup error (3). A thread started before the inventory existed skips it and says so.
- The source inventory lists every class with `InitializeComponent` in the designer files under `Chummer/` and `Core/`: its controls (type, container, text, tag, context menu) and its event bindings with each handler's file and line. A binding it cannot read or a handler it cannot find is a setup error.
- `parity/inventory/scope.json` declares every class `active` or `deferred` and the events deferred everywhere, each with a reason. A new form or user control must be added to it; a class it lacks or names wrongly is a setup error.
- The coverage manifest lists every planned case and capture with the candidate side's outcome, every control of an active class as `observed` (in a recorded tree, in its class's subtree, a WinForms window within its parents' bounds whose automation ID is the control's name, or a tab page's shown tab item by its text), `windowless` (a declared type that is never a window, such as a tool strip item, and no tree matched it; left out of the controls counted) or `unobserved`, and every binding as `exercised` (a tab control's selection events, when a `selectTab` and no other acting action changed its visible page between two consecutive captures; or the events a performed `setValue`, `click` or `selectItem` raises on its control, when the capture just before it, with only `wait` and `waitFor` between, showed that control in one class), `unexercised` or `deferred`, and the control names no control matched. Presence in the source or on screen never counts as exercised.
- Observations describe only the source the candidate was built from: with capture runs, a working tree whose `Chummer/` or `Core/` differs from the build's record, or a candidate without a record, is a setup error. `npm run inventory -- --run <folder>...` builds the same documents from capture runs made with `--ui-tree` after an `npm start` build, and also requires each run's candidate to be that build; without `--run` it needs no build and observes nothing. `--help` lists its options.

## Interaction discovery

- `npm run discover -- --from <thread>` runs a discovery thread of its own LangGraph graph (`workflow/src/discovery/`), checkpointed in `out/discovery/checkpoints.sqlite`, with its folder in `out/discovery/threads/<thread>/`; `--resume <thread>` continues it with its original options, and `--help` lists the options (`--targets`, `--case-file`, `--settings-overlay`, `--threshold`, `--canonical-cache` or `--live-canonical`, `--unattended`). Its exit status is 0, 1 (an admitted scenario differs), 2 (its capture run had status 2 or invalid coverage, or a job failed with `invalid_output` or `refused`) or 3 (setup error, resumable).
- The baseline is the `--from` workflow thread's `inventory/` documents. Discovery fails with a setup error when the working tree's designer and code files or `parity/inventory/scope.json` differ from the baseline's, when the recorded candidate source differs from the working tree's compiled source, or when a baseline run captured another candidate than the recorded one: run `npm start` again first. It builds the capture tools, never the candidate.
- Targets (`targets.json`): the active classes' unobserved controls grouped by the tab pages that contain them, and tab controls whose selection bindings no run exercised; other unexercised bindings are counted as out of the actions' reach. One `rank` job ranks every target (with the archived fix changes most related to a target as priors in `priors/`), and the best `--targets` that are not `infeasible` get a `scenario` job each, side by side. Both read only, in scratch copies of their sealed context and the snapshot, like diagnosis jobs, with eval records, quota waits and the run budget.
- A plan is validated before it uses the lane: a fixture case of the case file, at most 24 `selectTab`, `waitFor`, `wait` or `capture` actions, one to four uniquely named captures ending the plan, tab texts the form's designer, the English language file's `Tab_` strings or the baseline's proofs know, and `waitFor` labels the active designers or the language file know. The valid plans run in one capture run with UI trees from the generated `cases.json`; a scenario proves only what the run's coverage manifest observed or exercised in its case and the baseline did not. Report each scenario's execution outcome apart from its visual outcome, and the run's execution outcome apart from its rows.
- A scenario that executed and proved something or differed is admitted to `parity/discovery/registry.json`, rendered into `parity/cases/discovered.json` (case names `<mode>-<file>@<scenario>`); the same fixture case and actions are a duplicate for the same source and replace the entry of another source. The fixture case file must not change while a thread runs, must not be `parity/cases/discovered.json`, and must have the startup delay and settle time the registry renders with (else a setup error). Discovery writes both into the working tree and never commits them; review and commit them together, and never edit one without the other: a case file that differs from the registry's rendering is a setup error. A default `npm start` captures them in its suite after the fixture cases (see Parity workflow); `npm start -- --case-file parity/cases/discovered.json` captures, compares, triages and diagnoses only them.
- A workflow thread discovers in its `discovery` stage, between `capture` and `conclude`, when every planned case captured and compared with status 0, its inventory ran and triage found no discrepancy and no other finding; otherwise it goes on to diagnosis as before. `--no-discovery`, `--no-diagnosis`, `--only`, a case file that is `parity/cases/discovered.json` and a thread stored before discovery ran in threads do not discover. Its discovery is the discovery thread `disc-<workflow thread>`, checkpointed and foldered like any discovery thread, with the workflow thread as its baseline, the thread's `--case-file` or else `parity/cases/characters.json` as its fixture case file (never the suite), the thread's settings overlay, threshold, canonical cache, unattended flag and rank and scenario configurations, and the profile's `discovery.targets` (default 3) as its targets. A resumed workflow thread resumes an unfinished discovery thread and reads a finished one's conclusion without running it again. A discovery setup error ends the run with 3, and resuming the workflow thread resumes the discovery. The thread records the discovery thread, its exit status, the cases it admitted and those of them that differ; the end-of-run report prints them on a `Discovery:` line after the triage and inventory lines, and the thread then concludes.
- Rank and scenario records get an automatic `discovery` label (`proven`, `not-proven`, `untested`, `invalid-plan`, `execution-failed`, `abstained`). `discovery.json` holds the targets, each scenario's plan, validation, execution, visual outcome, proofs and admission, the run, and the coverage and registry before and after.

## Diagnosis

- After triage, each cluster gets a sealed context under `out/workflow/threads/<thread>/diagnosis/<cluster>/` (`context.json`, the crops in `evidence/`) over a history-less snapshot of `Chummer/`, `Core/`, `bin/data/` and `bin/lang/` in `diagnosis/source/`. Prompts are built from the context only; every job records its hash. The build step records the identity of the compiled source (`Chummer/` and `Core/`, by content) next to the candidate, and diagnosis ends with a setup error when the snapshot's compiled source differs from it or none is recorded, `--only diagnose` included: the snapshot must be the source the candidate was built from. `bin/data` and `bin/lang` are capture inputs and not part of this guard.
- A cluster gets `diagnosis.hypotheses` hypothesis jobs (profile, 1 to 3, default 1), each in a fresh session from the same sealed context, then a challenge job in a fresh session for each hypothesis that did not abstain; jobs of every cluster fan out with `Send` up to the model pool size. A cluster is abstained only when every hypothesis abstained, and failed when any of its jobs failed with `invalid_output` or `refused`. Answers are validated against the snapshot (cited files and lines exist) and the check vocabulary (the case file's cases and captures); a failed validation is `invalid_output`.
- Jobs are read-only, and each runs in a scratch copy of its context and the snapshot outside the repository (removed afterwards), because the Codex sandbox limits writes but not reads. The Claude adapter runs the Claude Code CLI headless with only Read, Grep and Glob, without allowance rules, and the job fails unless the model opened each evidence image with a Read that succeeded (Codex gets them as image inputs); the Codex adapter runs the Codex SDK in its read-only sandbox without web search. Both run under the subscriptions: API-key variables are removed, and a job that would bill an API key fails as `infra`.
- Failures: `invalid_output` and `refused` fail the cluster (exit status 2); `infra` and `timeout` (a job past its time limit) are setup errors (status 3, resumable); `quota_exhausted` routes to `wait_for_quota`, which waits 1, 2, 5, 10, 15 minutes, then every 15 minutes, and retries at once after a restart. Quota waits are not charged to the run budget, which is checked when a job gets its place in the model pool.
- One check capture on the desktop lane covers the predictions of every hypothesis and alternative of every cluster (union of cases and captures). Each hypothesis is judged with its own alternative and is `confirmed`, `refuted` or `undecided`; a cluster is `confirmed` when any of its hypotheses is, `refuted` when every hypothesis that predicted is, else `undecided`. Report the check's execution outcome apart from its observations.
- Every job is an eval record in `out/workflow/store.sqlite` (namespace `eval-record/<job kind>`), labelled with the check outcome of its own hypothesis (origin `workflow`; see Evaluation for the other labels). `out/workflow/threads/<thread>/diagnosis.json` lists each cluster's jobs, check outcome and record IDs, the first hypothesis's answers at the cluster's top level as with one hypothesis, in `hypotheses` every hypothesis with its status, answers and records, and in its check's `variants` each judged hypothesis's outcome; the end-of-run report names each hypothesis of a cluster with several and its outcome. A thread stored with one hypothesis per cluster reads as one; the agents' raw streams are in `diagnosis/logs/`.
- The profile's `agents` sets, per job kind under `agents.jobs.<kind>` (`hypothesis`, `challenge`, `grade`, `repair`, `rank`, `scenario`, `tune`), `provider` (`claude` or `codex`), `model`, `effort` and `timeoutMinutes`, plus `modelPool`, `runBudgetMinutes` and `executables.claude`/`executables.codex`. By default hypotheses, grades, repairs, the discovery jobs and tuning proposals run on Claude and challenges on Codex. The Claude Code CLI must be on `PATH` or named in `executables.claude`.

## Repair

- After diagnosis, each cluster whose check outcome is `confirmed` gets a repair attempt (job kind `repair`), and further ones only as next attempts (see Loop); attempts fan out with `Send`, their builds run in the CPU pool and their checks on the first free desktop lane. `--no-repair` and `--only` run no repair.
- Before the first attempt the thread's source is committed once on the local branch `workflow/<thread>/source`: the commit the snapshot was taken on, or a commit on it of the snapshot's `Chummer/`, `Core/`, `bin/data/` and `bin/lang/` when the working tree differed, made with a private index; the working tree, the index and the checked-out branch never change. A resumed thread uses the branch as it finds it, and a source branch whose content is not the snapshot's is a setup error.
- An attempt makes `repair.tries` tries (profile, 1 to 3, default 1) per confirmed hypothesis of its cluster, at most 6 in all, started side by side; they are numbered round by round (the first try of each confirmed hypothesis in order, then the second, …), and the tries past the sixth are left out. Each try is a repair as described below, with its own record `<attempt record>/try-<k>`, worktree and branch `workflow/<thread>/repair/<cluster>/attempt-<n>-try-<k>`, its hypothesis's answer, challenge and observations in its prompt, and its own guard, build and narrow check; an attempt of one try keeps the attempt's record and branch `workflow/<thread>/repair/<cluster>/attempt-<n>`. Every try's worktree starts at the source commit. The attempt passes when a try passes and selects, among the passed tries, the one with the fewest added plus removed lines, then the fewest files, then the lowest try number; the other passed tries stay `passed` and not selected. A rejected attempt's reason lists each try's stage and reason; when no try passed and a try's job failed with `invalid_output` or `refused`, the attempt fails, as an attempt of one try whose job failed so does. A usage limit in any try parks the whole attempt until the quota wait ends and it starts again under a new number; the jobs that finished are charged, and a try already building finishes its build and narrow check, whose result is discarded. The run budget is asked before each try's job: a try that cannot start is rejected at stage `model`, and the cluster is `budget_exhausted` only when no try finished.
- An attempt works in a scratch folder outside the repository: a `git worktree` on its own branch (see above), started at the source commit, and a read-only copy of the cluster's context. Claude gets Read, Grep, Glob, Edit and Write (no command tool) in accept-edits mode; Codex runs in a workspace-write sandbox without network, and a file change outside the worktree, or a change of the worktree's git state (its `.git` file, a commit of its own), fails the job as `infra`. When the job ends, the workflow commits every change git does not ignore on the try's branch (the try's commit; a job that changed nothing makes none). The worktree and the folder are removed when the attempt ends; the branches and their commits stay.
- The patch is what differs between the source commit and the try's commit (none without a commit; ignored files are no change). The guard rejects it before a build when it is empty, differs from the files the answer lists, changes anything outside `Chummer/` and `Core/`, deletes a file, holds a NUL byte, changes only a file's mode, or changes more than 10 files or 300 lines.
- The patched worktree is built by `parity/scripts/build-candidate.mjs --source <worktree> --output <folder> --log <file>` (exit 0 built, 1 failed, 3 setup error) into the try's own folder, never into `bin/` or `out/candidate/`. The narrow check is one capture runner call with `--candidate-exe` set to the attempt's executable, the cluster's cases and captures, and the thread's case file, overlay, threshold and canonical cache. It passes only with exit 0 and valid coverage; report its execution outcome apart from its visual result.
- `repair.deadlineMinutes` in the profile (default 60) bounds an attempt's model jobs and builds, one deadline for all its tries; past it a try is rejected at stage `deadline`. The narrow check is not cut off.
- Every attempt whose model job finished is archived in `out/workflow/threads/<thread>/repair/<cluster>/attempt-<n>/` (`attempt.json`, `patch.diff`, `files/before|after/`, `build.log`) with its outcome, `passed` or `rejected` at stage `model`, `deadline`, `patch`, `build` or `check`, and the reason. Each try is in `try-<k>/` with its own `attempt.json` fields (try, hypothesis, outcome, record, branch, check), patch, files and build log; the attempt's `attempt.json` lists them in `tries`, names the selected one in `selectedTry` and keeps the selected try's branch, commit, patch, build and check at its top level. `repair.json` lists each cluster's repair with the latest attempt's tries, and the end-of-run report gives a line per try (hypothesis, changed lines and files, branch, `SELECTED` or `not selected`, outcome, reason) with its narrow check's execution outcome apart from its visual result. An attempt's eval record, or with several tries each try's, gets the automatic `repair` label; repair records stay out of the review queue, the grader and datasets.

## Widening

- After repair, each passed attempt is widened without a model, only through its selected try (the commit at the top level of its `attempt.json`; the tries not selected are never widened, promoted or rolled back), one cluster at a time in cluster ID order, on the accepted source: the thread's source commit plus the attempts promoted before it. `--no-widening`, `--no-repair` and `--only` run no widening.
- The widened source is a `git worktree` in `out/workflow/threads/<thread>/widening/<cluster>/attempt-<n>/source/` on its own branch `workflow/<thread>/widening/<cluster>/attempt-<n>`, started at the accepted commit (the tip of `accepted/<thread>`, before the first promotion the source commit). The selected try's commit is applied to it with git, without a commit, only when every file it changes has in the accepted commit the blob it had in the try commit's parent and every file it adds is absent there (else rejected at stage `apply`, naming the files), and the worktree is built into `widening/<cluster>/attempt-<n>/build/` in the CPU pool (exit 1: stage `build`).
- The levels run in order, each one capture runner call with the widened build as candidate and the thread's case file, overlay, threshold and canonical cache, over the whole case file whatever `--case` and `--capture` the thread had: `narrow` (the cluster's cases and captures), `character` (every capture of those cases), `mode` (the other cases of their modes) and `suite` (the rest). A level without a case passes as nothing new; the first failing level ends the ladder. Before each level or baseline capture the thread's canonical executable and support files, overlay and capture tools, and the capture runner's environment fingerprint (taken when the thread starts), must be those it started with, and a run must cover only its selected cases; otherwise the run ends with a setup error.
- Every row of a level that is not within the threshold is attributed against the newest row of the same case and capture in a run of the accepted source (the thread's captures and its check run, except runs with status 2 or invalid coverage, after a promotion the promoted attempt's level runs): `target` (a member of the cluster), `introduced` (the baseline passed), `changed` (the candidate's pixels moved beyond the threshold), `pre-existing` (same candidate pixels) or `unattributed`. Rows without a baseline are first captured on the accepted build (the snapshot is built once into `widening/accepted/`). Only `pre-existing` rows let a level pass. A level or baseline capture with status 2 or invalid coverage fails the level as an execution failure and makes the run's status 2; report each level's execution outcome apart from its visual result.
- An attempt whose four levels pass is promoted: every change of its widened worktree that git does not ignore is committed on its widening branch (the fix commit, whose parent is the accepted commit), and `accepted/<thread>` is moved to it by a compare-and-swap ref update (created at the first promotion, so it starts with the source commit's history); the repository's working tree, index and checked-out branch never change. The commit's `Repair-Record` trailer lets a resumed promotion find it. The promoted worktree and build become the accepted source and build for the next cluster. A failed attempt is rolled back: its worktree and build are removed, its widening branch stays, and the accepted branch and source stay as they were. A passed attempt archived without a commit cannot be widened (setup error: start a new thread). A verified attempt whose staged tree equals the accepted tree has nothing to commit and is rejected at stage `promote`.
- `widening/<cluster>/attempt-<n>/widening.json` and the thread's `widening.json` (with the earlier widenings of clusters that got a next attempt) hold every level with its run folders, execution outcomes and attributions, the outcome, the commit and the selected try (`selectedTry` of `tries`); the selected try's repair record gets the automatic `widening` label. Delete an `accepted/<thread>` branch or a branch under `workflow/<thread>/` you do not want with `git branch -D` only when its thread is finished: a thread that can still be resumed needs its branches where it left them, and a promotion that finds the accepted branch moved or gone is a setup error. The workflow never pushes or deletes them.

## Loop

- After widening (after repair when widening is off), a cluster whose latest attempt was rejected, by repair or by widening, gets a next attempt while its attempts are fewer than `repair.maxAttempts` in the profile (default 2) and the run budget is not spent; a passed next attempt is widened on the source accepted so far. No next attempt follows an execution failure (any try's narrow check, a level or baseline capture with status 2 or invalid coverage) or a rejection at widening stage `apply` or `promote`. A next attempt starts at the thread's source commit, and its prompt lists the cluster's earlier attempts with their patch, stage and reason, every try of an attempt of several with its own (`repair.json` lists them too).
- Every run that triaged ends in `conclude`, which writes `out/workflow/threads/<thread>/outcome.json` and prints a `Loop <cluster>:` line per cluster, a `Merge:` line when anything was promoted and an `Outcome:` line. Each cluster ends `fixed` (promoted and merged, see Merge), `merge_failed` (promoted and not merged, with stage `merge`, the reason and the fix's commit) or at the stage where it stopped: `not_diagnosed`, `diagnosis_failed`, `abstained`, `refuted`, `undecided`, `not_repaired`, `repair_failed`, `repair_rejected`, `not_widened`, `widening_rejected`, or `budget_exhausted`. The outcome is `verified_for_scope` when every cluster is fixed, no planned case's capture or compare had status 2 and triage listed no other findings; else `budget_exhausted` when a cluster stopped for the budget; else `findings_remaining`. `outcome.json` also holds the scope, its problems, each cluster's commit and merge commit, the accepted branch, `merge` (see Merge), the measures (clusters, fixed, fix rate, attempts, model time, elapsed time) and `discovery`: null when the thread did not discover, else the discovery thread, its exit status, the cases it admitted, those of them that differ and its `discovery.json`. The outcome stays about the planned scope: an admitted scenario that differs does not change it, and the next default run captures it. Report the outcome beside the exit status, and the execution outcomes apart from the visual results as before.

## Merge

- A thread records, when it starts, the branch the repository's `HEAD` names and its commit. A thread that repairs and widens with a detached `HEAD` ends with a setup error before the build and stores nothing; check out a branch, or pass `--no-repair` or `--no-widening`.
- `conclude` merges every promoted fix into that branch, in the order of the promotions, in a worktree in `out/workflow/threads/<thread>/merge/` detached at the branch's tip: the fix commit is rebased from its parent onto the tip as `workflow/<thread>/fix/<cluster>` and merged with a merge commit of its own (`Merge fix for discrepancy <cluster>`, trailers `Workflow-Thread` and `Merged-Fix: <thread>/<cluster>`). A fix the branch has already still gets its merge commit, with the branch's tree. The worktree is removed afterwards.
- A rebase that conflicts is aborted: that cluster and every one promoted after it (verified on top of it) end `merge_failed`, the first naming the conflicting files and the later ones the first. When the thread's source held uncommitted edits of files the branch does not hold in the same state, the fixes were verified on top of them and none is merged either (`merge_failed`, naming the files); the thread concludes, so its fixes stay on `accepted/<thread>` and are not merged by resuming it.
- The merged tip is kept on `workflow/<thread>/integration`, then the branch is advanced to it: by a fast-forward in the worktree that has it checked out (the repository's own working tree, when it is checked out there), else by a compare-and-swap ref update. A branch that is no longer at the commit the merges were made on (any movement, also a reset to an earlier commit, while they were made), or a fast-forward git refuses (local edits of the merged files), is a setup error that names the integration branch; commit or stash the edits and resume the thread, which merges again onto the current tip and skips each fix whose `Merged-Fix` trailer the branch already holds.
- `outcome.json`'s `merge` holds the branch, its commit before and after, the integration branch and each fix with its fix branch and merge commit or reason; it is null when nothing was promoted. A thread stored before it recorded its start branch concludes its promoted fixes as `fixed` without merging, and `merge.skipped` says so. Nothing is pushed.

## Fix changes

- `npm start -- --fix-changes` works in fix changes; without it nothing below happens. The option is stored with the thread (a resumed thread keeps it) and cannot be combined with `--unattended`.
- Fix changes live in their own OpenSpec root, `fixes/`: `fixes/openspec/` holds the project-local schema `fix` (`proposal.md`, `tasks.md`, `verification.md`) and the archive `changes/archive/`. Never create fix changes in `openspec/changes/`, and never edit an archived one by hand: each is rendered from its `fix.json` record. `npm run fixes:validate` validates them with the pinned CLI.
- Diagnosis: every archived fix change of the working tree is scored against each cluster (8 for the same image hash, 3 per shared capture, 1 per shared case, up to 4 for shared OCR words); the best three that share anything are copied into the context's `priors/` and listed in `context.json`, and the hypothesis prompt (version `hypothesis-v2+priors-v1`) presents them as leads to verify in the snapshot. The challenge job does not see them (its prompt, its copy of `context.json` and its folder hold none), and eval runs stage every context the same way, so they measure `hypothesis-v2`. A `fix.json` that does not parse is a setup error.
- Repair: an attempt starts with a read-only plan job (job kind `repair`, prompt `repair-plan-v2`, the attempt's record) that splits the fix into 1 to 5 subtasks with their files and blockers (lower subtasks only; subtasks that may run together name different files). Each subtask whose blockers are done runs as a writable job (`repair-task-v2`, record `<attempt record>/task-<k>`) in its own worktree on `workflow/<thread>/repair/<cluster>/attempt-<n>-task-<k>`, started at a commit on the source commit that holds its blockers' changes, in parallel up to the model pool; its changes are committed on its branch. The changes are joined in order onto the source commit by blob; a subtask whose changes differ from its answer, or a file two subtasks changed without one blocking the other, rejects the attempt at stage `patch`. The join is committed in the try's worktree as its commit, which then goes through the guard, build and narrow check. A subtask's worktree is removed when it ends; its branch stays. `attempt.json` adds `planned` (the plan and each subtask), and a passed attempt's archive holds the draft in `fix/`. With several tries each try plans and implements on its own (records `<attempt record>/try-<k>` and `<attempt record>/try-<k>/task-<j>`, subtask branches `attempt-<n>-try-<k>-task-<j>`), and the selected try's plan and draft are the attempt's.
- Promotion: the draft gets the widening's levels, is created, validated (strict) and archived by the OpenSpec CLI in `widening/<cluster>/attempt-<n>/fix-change/`, and the fix commit on `accepted/<thread>` holds the archived change at `fixes/openspec/changes/archive/<date>-fix-<cluster>-<thread suffix>/` beside `Chummer/` and `Core/`. Merging the fix into the branch the thread started on (see Merge) adds it to the repository's archive, where later threads retrieve it.

## Evaluation

- `npm run eval -- <command>` (`--help` lists them) works on the eval records of `out/workflow/store.sqlite` and writes under `out/evals/`; it exits with 0, 1 (certificate refused), 2 (a grader job failed) or 3 (setup error). Evaluation is for prompts and the process around them; deterministic code is covered by tests.
- A record has four labels, kept apart: `check` (the check outcome of its hypothesis), `hindsight` (graded against an accepted fix), `review` (a person's verdict) and `grader` (an advisory model score). Only hindsight grades and `correct` or `wrong` verdicts are gold; a grader score only orders the review queue. Its `origin` is `workflow`, `eval-run` or `grader`; the queue, the grader and datasets use `workflow` records only.
- `benchmark add --cluster <id> --fix <commit> --mechanism <class>` writes a benchmark item to `workflow/evals/benchmark/` (commit it) for a fix a person accepted; `--regression <commit>` names the change that caused the discrepancy, and a fix that mostly undoes it is a `revert`. `benchmark check` verifies that the items still replay; `hindsight` grades the answers given before each fix.
- `grade` runs the advisory grader (job kind `grade`) on answers without a grade. `queue` prints the review queue: every hypothesis whose check and hindsight disagree, then a sample per job kind and check outcome, the grader's least certain first. `npm run review` serves the queue on `http://127.0.0.1:4317/` with the crops, their difference, the answer and the fix's patch; a verdict is stored with the OS user as reviewer.
- `freeze --job <kind> --name <name>` writes a new, never-changed dataset version to `out/evals/datasets/<name>/v<k>/` with copies of the contexts and snapshots, the observed captures and the gold root cause; a cluster's items lie in one partition (`test` or `development`), and a new version of a name keeps the seed and test percentage of the one before it. `--job rank|scenario` freezes the labelled discovery records whose context is still in their discovery thread: a scenario item's gold is its proven plan's case and tabs, a rank item's the targets its thread proved and ran without proof; scenario items are partitioned by target.
- `run --dataset <folder>` runs the current prompt with the profile's agent choice on a partition (`--partition`, default `test`; `--repeat`; the repetitions of an item are one sample in every interval, which counts items) and scores each answer (`prediction` against the observed captures, `rootCause` against gold); `run --resume <run>` finishes a stopped run with its stored settings. `compare --baseline <run> --candidate <run>` reports the paired difference with its 95% t interval and a verdict; report the interval and n with every delta.
- `compare-threads --baseline <threads> --candidate <threads>` compares finished workflow threads (comma-separated IDs, each with its `outcome.json`) in pairs by cluster ID: the fix rate (1 for `fixed`) and the model time of each cluster's workflow records, with each side's mean, the mean paired difference, its 95% t interval and a verdict (`too-few-pairs` below two pairs). A cluster on one side only is listed apart; a cluster twice on one side is a setup error. Report the interval and n with every delta, as for `compare`.
- `certify --run <run> --metric <m> --min-pass <rate>` writes `<job kind>.json` to the certificates folder (the profile's `certificates`, else `workflow/evals/certificates/`) when the lower bound of the 95% Wilson interval, over the items of the test partition, meets the rate. Rank and scenario runs score `valid` (the answer passes its validation and, for a scenario, the plan validator; an abstention has no value) and `reached` (the best feasible target was proven; the plan selects the proven plan's tabs) instead of `prediction` and `rootCause`, and `compare` (default: the job kind's first metric) and `certify` refuse a metric the job kind does not score. `npm run discover -- --unattended` starts only when `rank` and `scenario` have certificates for their provider, model, effort and prompt version. `npm start -- --unattended` starts only when `hypothesis` and `challenge` have certificates for the run's provider, model, effort and prompt version, and `rank` and `scenario` too when the thread may discover, and only with `--no-repair`, since no certificate covers repair jobs.

## Tuning

- A tuning configuration (`npm run eval -- tune …`, `--help` lists the commands) changes only how a `hypothesis`, `challenge`, `rank` or `scenario` job is prompted: up to six lines of guidance in a section after the instructions, and the context `inline` or as a `file` the job reads. It names the prompt version it extends (a prompt edit in the code makes it stale, a setup error wherever it is used), its ID is `tuned-` and 12 hex digits of its content hash, and its jobs record `<prompt version>+<ID>`. Validation and scoring do not change.
- The tuning folder (the profile's `tuning`, else `workflow/evals/tuning/`) holds `active/<jobKind>.json` (the active configuration, the ones it replaced and the ones rolled back, each with its certificate) and the holdout ledger `holdout.json`. Activation and rollback write them and the certificate into the working tree: review and commit them together. Candidates are in `out/evals/tuning/candidates/`, cycles in `out/evals/tuning/cycles/`.
- `npm start` and `npm run discover` store the active configurations of the job kinds they dispatch in a new thread's options (a workflow thread that may discover also those of `rank` and `scenario`, which its discovery thread uses); a resumed thread keeps them. `eval run` measures the active configuration by default, `--tuning none` the code's prompt and `--tuning <ID>` a candidate, which may not run on `test` or `all`.
- `tune add --file` stores a person's candidate; `tune propose --run <run>` has a `tune` job (record origin `workflow`, kept out of review, grading and datasets) propose one from a complete development run, seeing its samples, answers, scores and the items' gold, and never the test partition.
- `tune holdout` starts a candidate's test run only when its development run beat the active configuration's on the same samples and agent choice (a higher mean of the metric, or the same mean in less model time, with a value on every repetition of every item the active configuration has one on) and the ledger allows it (a test item is shown to a candidate once and to three candidates at most: an exposure counts against every dataset of the job kind whose test partition holds one of its items, whatever its name, version or seed); the exposure is recorded before the run starts, and a run never created starts when `tune holdout` is asked again. `tune activate` needs that run complete, not `worse` than a test run of the active configuration on the same samples with a value wherever that has one, and the certificate rule; it writes the certificate for the tuned prompt version (asked again for the same run, it writes it again). `eval certify` certifies only a run of the active configuration. `tune rollback --job <kind>` restores the previous entry and its certificate. Report every delta with n and its 95% interval.
- `tune cycle` runs a development baseline, up to three proposals with their development runs, the holdout, a test baseline and the activation, recording each run ID in `cycle.json` before the run starts; `--resume <cycle>` continues it. Exit status: 0 `activated` or `no_improvement`, 1 `rejected` (also a refused holdout or activation), 2 `failed` (a `tune` job failed), 3 setup error.

## Desktop use

- The optional local profile may declare `lanes`: one local desktop or up to eight named lanes in total. For example, `"lanes": [{"name":"desktop"},{"name":"vm","agent":"D:\\shared\\lane-vm"}]`. Each agent folder must be visible at the same absolute path to the workflow and its serving session; that session must also see the repository and every command path there. Each lane must use a distinct host and user pair, and all lanes must have the same capture environment fingerprint. A lane in another session runs the capture runner with the thread's `canonicalCache` and `settingsOverlay` paths unchanged, so when an agent lane is declared they must name folders that session can read and write at those paths (not the workflow user's `%LOCALAPPDATA%`). A settings overlay it cannot read fails the capture with status 3; a cache folder that does not exist there is created on that lane's machine, and the lanes then stop sharing canonical sides. The lane agent runs the command of every request in its folder as its own user, so only the workflow's user and the agent's user may write that folder. The default is the one local `desktop` lane.
- In the other interactive session, run `npm run lane-agent -- --folder <dir>` before `npm start`. The agent serves requests until Ctrl+C and locks that session's desktop while capturing. Its folder holds request logs and exit records. A missing or silent agent ends the workflow with a setup error; resume the printed thread after restoring the lane.
- An agent lane may declare `"rider":{"endpoint":"http://127.0.0.1:port/stream","rootFolder":"<repository path>","configuration":"Lane agent"}`. Rider must have that project open and its MCP endpoint reachable. The workflow starts the run configuration if the agent is absent, then dispatches through the agent folder. `.run/Lane agent.run.xml` takes its folder from `LANE_AGENT_FOLDER`.
- A capture run drives real windows. Only one live run may use a desktop at a time: never start a second run while one is active, and watch a slow run instead of restarting it. The workflow's capture steps hold the lock of the lane they use (this machine's desktop: `%LOCALAPPDATA%\ChummerGenSR4\desktop-lane.lock`; an agent lane: `lane.lock` in its folder) and wait for each other; `npm run parity` takes none.
- Leave the mouse and keyboard alone during a run; another window taking the foreground fails the current action with a `window-activation` reason. The capture runner parks the pointer in the middle of the app's title bar, and a pointer moved away from it fails the next capture with a `pointer` reason.
