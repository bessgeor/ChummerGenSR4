# Agent guide

## OpenSpec workflow

- Every change is an OpenSpec change under `openspec/changes/<change-name>/` using the `spec-driven` schema. Project context and per-artifact rules live in `openspec/config.yaml`; the CLI feeds them into each artifact's instructions.
- Use the generated workflows: `/opsx:propose`, `/opsx:apply`, `/opsx:archive` in Claude Code, and the matching `openspec-*` skills in Codex. They are generated files; regenerate them with `npx openspec update` instead of editing them.
- Commit order on a change's branch:
  1. proposal, design, spec deltas and tasks (about eight tasks at most);
  2. small implementation commits;
  3. `verification.md`;
  4. `npx openspec archive <change-name>` as the final commit.
- Run `npm run openspec:validate` (strict) before every commit that touches `openspec/`. A failing validation blocks the change.

## One change per pull request

- A branch is named after its change and carries exactly that one change.
- Branch from `master`, or from the predecessor change's branch while its pull request is still open.

## Verification evidence

- Each change has `verification.md` beside its proposal. List the commands you ran and what they printed or produced.
- Keep fixture-tested scope separate from live evidence. When a live dependency is unavailable, list the requirement as unverified; fixture results never stand in for a live run.
- Preserve real failures: record a failed step as a failure with its output, never as a skip, a warning or a success. Report execution failures separately from visual differences.
- Mark a task done only when the evidence it names is recorded.

## Canonical executable

- `bin/ChummerGenSR4.exe` is the canonical build and is immutable. Never rebuild, replace, copy over or edit it.
- The app's Release configuration builds `ChummerGenSR4.exe` into `bin/`, so never build it with the default output path.
- Before and after any run that launches it, record its SHA-256. Both must equal `9ff3009946f0212842eb5aa803c3d8e1697752040229f52b25f584e7b0ae9e56`.

## Contracts

- Data read or written by more than one language is defined by a JSON Schema in `contracts/schemas/`. Edit the schema, then run `npm run contracts:generate`; never edit `contracts/generated/` by hand.
- Every schema needs an example in `contracts/examples/`. `npm run contracts:check` (drift), `npm run contracts:test` (TypeScript round-trip) and `npm run parity:test` (C# round-trip) must pass.

## Visual parity capture

- `npm run build:candidate` builds the app from the current source into `out/candidate/bin/`. Use it instead of building `Chummer/Chummer.csproj` yourself.
- `npm run parity` captures every case in `parity/cases/characters.json` on the canonical and the candidate executable in one run; `npm start` runs the parity workflow instead (see below). Pass options after `--`, for example `npm run parity -- --case Diego_v_alpha2_by_bessgeor --capture common`; `--help` lists them. In PowerShell, call `npm.cmd` instead of `npm`, because the `npm.ps1` shim drops the `--`.
- A run writes only under `out/runs/<runId>/`: staged apps, fixture copies, `captures/`, `summary.json`, `results.json`, `coverage.json`, `timing.json` and the comparer's `compare/`. The exit status is 0 (all passed), 1 (visual differences), 2 (execution failures) or 3 (setup error). Read `coverage.json` for execution (`valid`, `invalidReasons`, failures, and optional absences listed apart from them) and `results.json` for visual pass/fail, and report them separately. Invalid coverage alone gives status 2. `timing.json` holds the durations of every UI operation; it measures, it never decides an outcome.
- Run-specific settings go in a folder passed with `--settings-overlay`. Keep it outside the repository or under `out/`; never edit `bin/settings/` for a run.
- The fixtures use sourcebooks that `bin/settings/default.xml`, which enables only the core book, does not enable; without them the cases that need them fail at startup on both sides. To run the suite, pass an overlay holding `settings/default.xml`: a copy of `bin/settings/default.xml` (UTF-16) with these books added to `<books>`: `AR`, `AT`, `AU`, `DG`, `GH`, `RC`, `RW`, `SA`, `SDN`, `SG`, `SM`, `TOD`, `UCL`, `UN`, `WA` and `WAR`.
- `--canonical-cache <dir>` (outside the repository or under `out/`) reuses the canonical side of a case from an earlier run when every input it is keyed on is the same (the staged canonical app, the fixture, the actions, the screens and their scale, the OS build, the Windows colour and text settings, the app's registry options and the runner's own assemblies), and stores canonical sides that completed. A reused side is marked `cache` in the summary and in `coverage.json`, with the run that stored it; say so when you report a run. Leave the cache off for evidence that must show both executables running.
- Add a fixture to `parity/fixtures/characters/` only after reviewing its content (names, notes, links, images), and declare its mode in the case file.

## Visual parity compare

- `npm run compare -- --run out/runs/<runId>` analyzes a capture run: it reads `results.json` and replaces only `out/runs/<runId>/compare/` with `report.json` and the crops under `crops/`. `--no-ocr` turns OCR off; `--help` lists the options.
- The comparer's exit status is 0 (every row passed), 1 (differences reported), 2 (analysis failures: a row could not be analyzed, OCR failed, or a planned capture is unaccounted) or 3 (setup error, no report). The comparer needs the run's `coverage.json`.
- The report's `completeness` accounts for every planned capture: `reported`, `analysis-failed`, `filtered`, `optional-absent`, `execution-lost` or `unaccounted`. Report its totals with the comparer's outcome. Report the comparer's outcome apart from the capture run's execution outcomes and visual results.
- Discrepancies come only from the raw pixel difference. OCR text helps a reader; it never shows that a difference is gone or that two discrepancies are the same. Duplicates share the same changed pixels at nearly the same place.

## Parity workflow

- `npm start -- <options>` runs the LangGraph graph in `workflow/`: build (the candidate and the parity tools), then capture one case at a time with each captured case compared while the next is captured, then triage, then diagnosis, repair and widening, next attempts for rejected clusters, and the outcome (see below; `--no-diagnosis` ends the run after triage, `--no-repair` after diagnosis, `--no-widening` after repair; each of them still concludes). Capture options (`--case`, `--capture`, `--settings-overlay`, `--threshold`, `--case-file`) go to the capture runner, `--no-ocr` and `--tessdata <dir>` to the comparer; `--help` lists them. Each case gets its own run folder under `out/runs/`.
- The exit status is the highest capture and compare status of the cases (0, 1 or 2), 2 when a diagnosis or repair job failed a cluster or the check capture, a narrow check or a widening capture had execution failures, or 3 for a setup error; the thread's outcome (see Loop) never changes it. Report each case's execution outcome (capture status, coverage, where the canonical side came from) apart from its visual outcome (results, report status and completeness); the workflow prints both for every case at the end of the run, also with `--only`.
- Every run is a thread, checkpointed in `out/workflow/checkpoints.sqlite`; the thread ID is printed at the start. After a crash, Ctrl+C or a setup error, `npm start -- --resume <thread>` continues it with its original options.
- Capture and compare steps are keyed by their inputs and recorded under `out/workflow/steps/`. A step with the same inputs and intact outputs is reused, also by a new thread, and is reported as reused with the thread it came from. A capture key covers the machine environment the pixels depend on (screens and scale, OS build, Windows colour and text settings, the app's options); steps with status 2 are never reused, and `--recapture` captures every planned case again even when a step is recorded (a difference that looks like a paint race). `--only capture|compare|triage|diagnose` runs one node; the nodes before it must find recorded steps.
- Capture uses the canonical capture cache by default: `--canonical-cache <dir>`, else `PARITY_CANONICAL_CACHE`, else `canonicalCache` in the local profile, else `%LOCALAPPDATA%\ChummerGenSR4\canonical-cache`. All worktrees share it. Pass `--live-canonical` for evidence that must show the canonical executable running.
- Cache entries are keyed on the capture runner's assemblies, so every checkout must build them byte for byte: the parity and generated C# sources have their line endings pinned to CRLF in `.gitattributes`. Keep them CRLF when you write these files, and do not commit attributes that change it.
- The optional local profile (`PARITY_WORKFLOW_PROFILE` or `%LOCALAPPDATA%\ChummerGenSR4\workflow-profile.json`) may set `canonicalCache`, `settingsOverlay`, `cpuPool`, `agents` (see Diagnosis), `certificates` (see Evaluation), `repair.deadlineMinutes` (see Repair) and `repair.maxAttempts` (see Loop).
- Triage writes `out/workflow/threads/<thread>/triage.json`: discrepancy clusters across cases (same image hash, core at nearly the same place) with identities that stay the same across runs, and the rows and captures without pixel analysis listed apart.
- `npm run workflow:typecheck` and `npm run workflow:test` check the workflow; CI runs them with the parity build and `contracts:check`.

## Diagnosis

- After triage, each cluster gets a sealed context under `out/workflow/threads/<thread>/diagnosis/<cluster>/` (`context.json`, the crops in `evidence/`) over a history-less snapshot of `Chummer/`, `bin/data/` and `bin/lang/` in `diagnosis/source/`. Prompts are built from the context only; every job records its hash. The build step records the identity of the compiled source (`Chummer/`, by content) next to the candidate, and diagnosis ends with a setup error when the snapshot's `Chummer/` differs from it or none is recorded, `--only diagnose` included: the snapshot must be the source the candidate was built from. `bin/data` and `bin/lang` are capture inputs and not part of this guard.
- A hypothesis job runs per cluster, then a challenge job per hypothesis in a fresh session; jobs fan out with `Send` up to the model pool size. Answers are validated against the snapshot (cited files and lines exist) and the check vocabulary (the case file's cases and captures); a failed validation is `invalid_output`.
- Jobs are read-only, and each runs in a scratch copy of its context and the snapshot outside the repository (removed afterwards), because the Codex sandbox limits writes but not reads. The Claude adapter runs the Claude Code CLI headless with only Read, Grep and Glob, without allowance rules, and the job fails unless the model opened each evidence image with a Read that succeeded (Codex gets them as image inputs); the Codex adapter runs the Codex SDK in its read-only sandbox without web search. Both run under the subscriptions: API-key variables are removed, and a job that would bill an API key fails as `infra`.
- Failures: `invalid_output` and `refused` fail the cluster (exit status 2); `infra` and `timeout` (a job past its time limit) are setup errors (status 3, resumable); `quota_exhausted` routes to `wait_for_quota`, which waits 1, 2, 5, 10, 15 minutes, then every 15 minutes, and retries at once after a restart. Quota waits are not charged to the run budget, which is checked when a job gets its place in the model pool.
- One check capture on the desktop lane covers the predictions of every cluster (union of cases and captures). Each cluster is `confirmed`, `refuted` or `undecided`; report the check's execution outcome apart from its observations.
- Every job is an eval record in `out/workflow/store.sqlite` (namespace `eval-record/<job kind>`), labelled with its cluster's check outcome (origin `workflow`; see Evaluation for the other labels). `out/workflow/threads/<thread>/diagnosis.json` lists each cluster's jobs, check outcome and record IDs; the agents' raw streams are in `diagnosis/logs/`.
- The profile's `agents` sets, per job kind under `agents.jobs.<kind>` (`hypothesis`, `challenge`, `grade`, `repair`), `provider` (`claude` or `codex`), `model`, `effort` and `timeoutMinutes`, plus `modelPool`, `runBudgetMinutes` and `executables.claude`/`executables.codex`. By default hypotheses, grades and repairs run on Claude and challenges on Codex. The Claude Code CLI must be on `PATH` or named in `executables.claude`.

## Repair

- After diagnosis, each cluster whose check outcome is `confirmed` gets a repair attempt (job kind `repair`), and further ones only as next attempts (see Loop); attempts fan out with `Send`, their builds run in the CPU pool and their checks one at a time on the desktop lane. `--no-repair` and `--only` run no repair.
- An attempt works in a scratch folder outside the repository: a writable copy of the thread's `diagnosis/source/` snapshot, which has no version history, and a read-only copy of the cluster's context. Claude gets Read, Grep, Glob, Edit and Write (no command tool) in accept-edits mode; Codex runs in a workspace-write sandbox without network, and a file change outside the copy fails the job as `infra`. The folder is removed when the attempt ends.
- The patch is what differs between the copy and the snapshot. The guard rejects it before a build when it is empty, differs from the files the answer lists, changes anything outside `Chummer/`, deletes a file, holds a NUL byte, or changes more than 10 files or 300 lines.
- The patched copy is built by `parity/scripts/build-candidate.mjs --source <copy> --output <folder> --log <file>` (exit 0 built, 1 failed, 3 setup error) into the attempt's own folder, never into `bin/` or `out/candidate/`. The narrow check is one capture runner call with `--candidate-exe` set to the attempt's executable, the cluster's cases and captures, and the thread's case file, overlay, threshold and canonical cache. It passes only with exit 0 and valid coverage; report its execution outcome apart from its visual result.
- `repair.deadlineMinutes` in the profile (default 60) bounds an attempt's model job and build; past it the attempt is rejected at stage `deadline`. The narrow check is not cut off.
- Every attempt whose model job finished is archived in `out/workflow/threads/<thread>/repair/<cluster>/attempt-<n>/` (`attempt.json`, `patch.diff`, `files/before|after/`, `build.log`) with its outcome, `passed` or `rejected` at stage `model`, `deadline`, `patch`, `build` or `check`, and the reason; `repair.json` lists each cluster's repair. Its eval record gets the automatic `repair` label; repair records stay out of the review queue, the grader and datasets.

## Widening

- After repair, each passed attempt is widened without a model, one cluster at a time in cluster ID order, on the accepted source: the thread's snapshot plus the attempts promoted before it. `--no-widening`, `--no-repair` and `--only` run no widening.
- The patch from the attempt's archive is applied to a copy of the accepted `Chummer/` in `out/workflow/threads/<thread>/widening/<cluster>/attempt-<n>/source/` only when every file it changes still has the content the patch was made from (else rejected at stage `apply`), and built into `widening/<cluster>/attempt-<n>/build/` in the CPU pool (exit 1: stage `build`).
- The levels run in order, each one capture runner call with the widened build as candidate and the thread's case file, overlay, threshold and canonical cache, over the whole case file whatever `--case` and `--capture` the thread had: `narrow` (the cluster's cases and captures), `character` (every capture of those cases), `mode` (the other cases of their modes) and `suite` (the rest). A level without a case passes as nothing new; the first failing level ends the ladder. Before each level or baseline capture the thread's canonical executable and support files, overlay and capture tools, and the capture runner's environment fingerprint (taken when the thread starts), must be those it started with, and a run must cover only its selected cases; otherwise the run ends with a setup error.
- Every row of a level that is not within the threshold is attributed against the newest row of the same case and capture in a run of the accepted source (the thread's captures and its check run, except runs with status 2 or invalid coverage, after a promotion the promoted attempt's level runs): `target` (a member of the cluster), `introduced` (the baseline passed), `changed` (the candidate's pixels moved beyond the threshold), `pre-existing` (same candidate pixels) or `unattributed`. Rows without a baseline are first captured on the accepted build (the snapshot is built once into `widening/accepted/`). Only `pre-existing` rows let a level pass. A level or baseline capture with status 2 or invalid coverage fails the level as an execution failure and makes the run's status 2; report each level's execution outcome apart from its visual result.
- An attempt whose four levels pass is promoted as a commit on the local branch `accepted/<thread>` (started at the snapshot's commit, plus a commit of the snapshot's `Chummer/` when the working tree differed), made with a private index; the working tree, the index and the checked-out branch never change. The commit's `Repair-Record` trailer lets a resumed promotion find it. A failed attempt is rolled back: its widened source and build are removed and the accepted branch and source stay as they were. A verified attempt whose staged tree equals the accepted tree has nothing to commit and is rejected at stage `promote`.
- `widening/<cluster>/attempt-<n>/widening.json` and the thread's `widening.json` (with the earlier widenings of clusters that got a next attempt) hold every level with its run folders, execution outcomes and attributions, the outcome and the commit; the repair record gets the automatic `widening` label. Delete an `accepted/<thread>` branch you do not want with `git branch -D` only when its thread is finished: a thread that can still be resumed needs the branch where it left it, and a promotion that finds it moved or gone is a setup error. The workflow never deletes it.

## Loop

- After widening (after repair when widening is off), a cluster whose latest attempt was rejected, by repair or by widening, gets a next attempt while its attempts are fewer than `repair.maxAttempts` in the profile (default 2) and the run budget is not spent; a passed next attempt is widened on the source accepted so far. No next attempt follows an execution failure (a narrow check, level or baseline capture with status 2 or invalid coverage) or a rejection at widening stage `apply` or `promote`. A next attempt starts from the thread's snapshot, and its prompt lists the cluster's earlier attempts with their patch, stage and reason (`repair.json` lists them too).
- Every run that triaged ends in `conclude`, which writes `out/workflow/threads/<thread>/outcome.json` and prints a `Loop <cluster>:` line per cluster and an `Outcome:` line. Each cluster ends `fixed` (promoted) or at the stage where it stopped: `not_diagnosed`, `diagnosis_failed`, `abstained`, `refuted`, `undecided`, `not_repaired`, `repair_failed`, `repair_rejected`, `not_widened`, `widening_rejected`, or `budget_exhausted`. The outcome is `verified_for_scope` when every cluster is fixed, no planned case's capture or compare had status 2 and triage listed no other findings; else `budget_exhausted` when a cluster stopped for the budget; else `findings_remaining`. `outcome.json` also holds the scope, its problems and the measures (clusters, fixed, fix rate, attempts, model time, elapsed time). Report the outcome beside the exit status, and the execution outcomes apart from the visual results as before.

## Evaluation

- `npm run eval -- <command>` (`--help` lists them) works on the eval records of `out/workflow/store.sqlite` and writes under `out/evals/`; it exits with 0, 1 (certificate refused), 2 (a grader job failed) or 3 (setup error). Evaluation is for prompts and the process around them; deterministic code is covered by tests.
- A record has four labels, kept apart: `check` (its cluster's check outcome), `hindsight` (graded against an accepted fix), `review` (a person's verdict) and `grader` (an advisory model score). Only hindsight grades and `correct` or `wrong` verdicts are gold; a grader score only orders the review queue. Its `origin` is `workflow`, `eval-run` or `grader`; the queue, the grader and datasets use `workflow` records only.
- `benchmark add --cluster <id> --fix <commit> --mechanism <class>` writes a benchmark item to `workflow/evals/benchmark/` (commit it) for a fix a person accepted; `--regression <commit>` names the change that caused the discrepancy, and a fix that mostly undoes it is a `revert`. `benchmark check` verifies that the items still replay; `hindsight` grades the answers given before each fix.
- `grade` runs the advisory grader (job kind `grade`) on answers without a grade. `queue` prints the review queue: every hypothesis whose check and hindsight disagree, then a sample per job kind and check outcome, the grader's least certain first. `npm run review` serves the queue on `http://127.0.0.1:4317/` with the crops, their difference, the answer and the fix's patch; a verdict is stored with the OS user as reviewer.
- `freeze --job <kind> --name <name>` writes a new, never-changed dataset version to `out/evals/datasets/<name>/v<k>/` with copies of the contexts and snapshots, the observed captures and the gold root cause; a cluster's items lie in one partition (`test` or `development`), and a new version of a name keeps the seed and test percentage of the one before it.
- `run --dataset <folder>` runs the current prompt with the profile's agent choice on a partition (`--partition`, default `test`; `--repeat`; the repetitions of an item are one sample in every interval, which counts items) and scores each answer (`prediction` against the observed captures, `rootCause` against gold); `run --resume <run>` finishes a stopped run with its stored settings. `compare --baseline <run> --candidate <run>` reports the paired difference with its 95% t interval and a verdict; report the interval and n with every delta.
- `certify --run <run> --metric <m> --min-pass <rate>` writes `<job kind>.json` to the certificates folder (the profile's `certificates`, else `workflow/evals/certificates/`) when the lower bound of the 95% Wilson interval, over the items of the test partition, meets the rate. `npm start -- --unattended` starts only when `hypothesis` and `challenge` have certificates for the run's provider, model, effort and prompt version, and only with `--no-repair`, since no certificate covers repair jobs.

## Desktop use

- A capture run drives real windows. Only one live run may use the desktop at a time: never start a second run while one is active, and watch a slow run instead of restarting it. The workflow's capture steps hold a machine-wide lock (`%LOCALAPPDATA%\ChummerGenSR4\desktop-lane.lock`) and wait for each other; `npm run parity` does not take it.
- Leave the mouse and keyboard alone during a run; another window taking the foreground fails the current action with a `window-activation` reason. The capture runner parks the pointer in the middle of the app's title bar, and a pointer moved away from it fails the next capture with a `pointer` reason.
