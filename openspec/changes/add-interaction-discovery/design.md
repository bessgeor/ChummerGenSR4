# Design

## Context

`npm start` writes a coverage manifest for each thread (`interaction-inventory`): every control of the nine active classes as `observed`, `windowless` or `unobserved`, and every binding as `exercised`, `unexercised` or `deferred`, from the candidate side's UI trees. The case file's actions can select tabs, wait for a label, wait and capture. The model jobs run through `AgentRunner` with a per-job-kind agent choice, sealed contexts over a history-less source snapshot, eval records in the store and typed failures (`discrepancy-diagnosis`); evaluation freezes datasets of workflow records, runs prompts on them and certifies a configuration (`agent-evaluation`). Archived fix changes under `fixes/openspec/changes/archive/` are ranked as priors for hypotheses (`fix-changes`).

Most unobserved controls belong to pages the suite selects but whose content depends on the character or on a selected row; some are on pages no case selects. With only tab selection available, discovery can cover the second kind, and it must find out which is which.

## Goals / Non-Goals

**Goals:**
- Turn the manifest's gaps into ranked targets, and targets into scenarios in the case-file actions, with models doing the search and runs doing the proving.
- Never count coverage without a recorded tree that shows it, and never spend lane time on a plan that breaks the action vocabulary.
- Keep the scenarios that proved something as cases, so the workflow can capture, compare and diagnose them.
- Record every job for evaluation, and let certificates gate unattended discovery.

**Non-Goals:**
- Actions other than the case-file vocabulary: `selectTab`, `waitFor`, `wait` and `capture`.
- Running discovery inside `npm start`'s graph; discovery reads a finished thread instead.
- Diagnosing findings inside discovery: they reach diagnosis through the registry's case file.
- Retiring or superseding registered scenarios; the registry only grows, and a person edits it by hand to remove an entry (both files, which the loader checks agree).

## Decisions

**Discovery is its own command and graph.** `npm run discover -- --from <thread>` builds a LangGraph graph of its own (`workflow/src/discovery/`), checkpointed in `out/discovery/checkpoints.sqlite` under thread IDs `disc-<UTC>-<hex>`, with the workflow's store for eval records and the same desktop lane, CPU pool and model pool. `--resume <thread>` continues a thread with its stored options. *Why not a node of `npm start`:* the workflow's triage, diagnosis check and widening all work on the thread's case file; scenarios found halfway through would need a second case plan in every one of them. Discovery reads a finished thread and hands its results back as a case file. Options: `--from` (required), `--case-file` (the fixtures, default the suite), `--settings-overlay`, `--threshold`, `--canonical-cache` or `--live-canonical` (the same defaults as `npm start`), `--targets <n>` (how many targets get a scenario job, 1 to 10, default 3) and `--unattended`.

**The baseline is the thread's inventory, and it must describe the candidate that discovery runs.** The `prepare` node reads `out/workflow/threads/<from>/inventory/source-inventory.json` and `coverage-manifest.json`, builds the source inventory of the working tree again and requires the same source hash; requires the recorded candidate source to equal the working tree's compiled source (as the inventory does); and requires every baseline run's candidate SHA-256 to equal the one the build recorded. A missing document or any mismatch is a setup error. It then builds the capture tools (not the candidate) and fingerprints the environment, as the workflow's build node does with the candidate build off. It records the SHA-256 of the fixture case file and of the two baseline documents; every later node that reads them fails with a setup error when one changed, because the targets and sealed contexts describe them.

**Targets.** The prompts say that a tab page itself counts as shown only when its tab text equals its designer text, so a page the app renames can show its controls but never the page control. A target is either a group of `unobserved` controls of one active class that share the chain of tab pages containing them (from the designer containment; a control on no tab page has an empty chain), with ID `<Class>/<page>/<page>` by page control names or `<Class>/-`, or a tab control of an active class with an `unexercised` selection binding (`SelectedIndexChanged`, `Selected`, `Selecting`, `Deselecting`, `Deselected`), with ID `<Class>.<tabControl>#selection`. Controls and bindings proved by a registry entry recorded for the same source hash count as covered and leave their targets; a target with nothing left is dropped. Every other unexercised binding needs an action the vocabulary does not have, and `targets.json` lists their count per event as out of reach, without targets.

**Rank job.** One `rank` job sees `rank/context.json`: every target (its class, page chain with designer texts, controls with type and text, or tab control and pages), the fixture cases of the case file (name, mode, form class, the tab names their actions select, their captures, and a copy of each character file in `fixtures/` under its case name, since the snapshot holds no fixture and the code that shows a page often depends on the character's build method or enabled attributes), the known tab texts per form class, and the priors; and the snapshot beside it. It answers with a ranking of every target exactly once: a score from 0 to 1, a feasibility (`feasible`, `uncertain`, `infeasible`), the fixture case it would use or none, and a reason. A target missing or repeated, an unknown case, or an empty reason fails validation (`invalid_output`). The `select` node then takes the `--targets` best targets by score (then by ID) that are not `infeasible`. *Priors:* every archived fix change is scored against each target (3 when its patch changes the target class's code or designer file, 1 per fixture case of the target's mode among its cases, up to 4 for the Jaccard share of the words of its OCR texts among the words of the target's control texts and page texts), and the best three of the whole ranking that share anything are copied into `priors/` and listed with their scores and reasons, as diagnosis does. A `fix.json` that does not parse is a setup error.

**Scenario jobs fan out.** `route_scenarios` sends one `scenario` job per selected target; each sees `scenario-<n>/context.json` (the target, its rank, the fixture cases with their full actions and character files, the known tab texts, and `labels.json`, the known `waitFor` texts; every file a context lists carries its SHA-256, checked whenever the context is read again) and the snapshot. It answers with a plan (`case`, `actions`, `expect`: the target's controls it expects to show, and a reason) or abstains with a reason. The job's validation checks only the answer's references and reason: a known case, expected controls that belong to the target (for a selection target its tab control and pages), and a non-empty reason. Both job kinds read only (Read, Grep and Glob for Claude, the read-only sandbox for Codex), in a scratch copy of the context and the snapshot, like diagnosis jobs. A usage limit routes to a wait node (`wait_for_rank_quota`, `wait_for_scenario_quota`) that waits as diagnosis does; `infra` and `timeout` end the run with status 3, resumable; `invalid_output` and `refused` fail that job (exit status 2). The run budget (`agents.runBudgetMinutes`) is charged with model time and checked when a job gets its place in the pool; a job that finds it spent is not started and its target ends `budget_exhausted`.

**The plan validator is deterministic and comes before the lane.** A plan is valid when: its case is a fixture case of the case file; it has at most 24 actions, each `selectTab` (a `name` and no `optional`), `waitFor` (a `label`), `wait` (`milliseconds` from 0 to 10 000) or `capture` (a `name` matching `^[a-z0-9][a-z0-9-]*$`); it has one to four captures with unique names and ends with a capture; every `selectTab` name is a known tab text of the case's form class (`frmCreate` for build, `frmCareer` for career): a designer text of one of its tab pages, a `Tab_` string of the English language file, or a page a baseline tree showed for that class; and every `waitFor` label is a designer text of a control of an active class or a string of the English language file. A rejected plan gets the outcome `invalid-plan` with every reason and no lane time. *Why not in the job's validation:* a plan the vocabulary rejects is a legitimate result to measure, not a broken answer, and it must not end the run.

**Execution is one capture run.** The `execute` node writes `cases.json` in the thread folder: the fixture case file's startup delay and settle time, empty mode actions, and one character entry per valid plan with its fixture path (relative to the generated file), mode, `scenario` name and `actions`. The scenario name is the target ID in lower case with every other character run replaced by `-`, cut to 48 characters, plus `-` and the first 8 hex digits of the SHA-256 of the canonical JSON of the target, the case name and the actions, so two targets never share a case name; the case is `<case>@<scenario>`. Before the run it checks the capture inputs and the capture runner's environment fingerprint against the ones the thread started with, as widening does before each level. It then runs the capture runner once on the desktop lane with that case file, every generated case, `--ui-tree`, and the thread's overlay, threshold and canonical cache. Exit 3 or a run that covered other cases is a setup error. *Why one run:* the lane is the scarce resource and each scenario is independent.

**Case files carry scenarios.** `parity-cases.schema.json` gives a character entry two optional fields: `actions`, which replace the mode's actions for that entry, and `scenario` (`^[a-z0-9][a-z0-9-]*$`), which names the case `<mode>-<file>@<scenario>`. `scenario` without `actions`, `actions` without `scenario` and an empty `actions` list are errors, so two entries of one fixture never share the suite's case name. The C# loader and the workflow's case plan read them the same way; `--case` matches a case by case name, file name or file name without extension, as for any case file.

**Proof comes from the scenario run's trees.** The `register` node reads the run like the inventory does (`readRunObservation`) and builds a coverage manifest over the generated cases with the same source inventory and scope. Per scenario: the execution outcome is `executed` when both sides have no failure, nothing not run, contiguous records and no invalid reason of the coverage audit for the case, else `execution-failed`; the visual outcome is `clear` when every result row of its case is within the threshold, else `finding` with the differing captures; the proofs are the controls that were not observed in the baseline (nor proved by the registry) and are observed in its case, and the selection bindings unexercised there and exercised in its case. A scenario is `proven` when it executed and has a proof, `not-proven` when it executed without one. Coverage is never taken from the plan, the expected controls or the model's words.

**The registry keeps what a run proved.** `parity/discovery/registry.json` holds one entry per admitted scenario: the case, the fixture case, mode, scenario name, actions and their hash, the target, the source hash, the proofs, the visual outcome with the differing captures, the discovery thread, run ID and record IDs, and the time. A scenario is admitted when it executed and either proved something or showed a finding; one whose fixture case and actions an entry of the same source hash already has is a `duplicate` and is not admitted again, and an entry of another source hash with them is replaced (its proofs no longer count). A register step that runs again after an interruption leaves its own thread's admissions out of the earlier proofs and the duplicates, so it decides the same. A registry without entries is never written, since its case file would hold no character. The registry is rendered into `parity/cases/discovered.json` (the fixture case file's timings, empty mode actions, one character entry per registry entry in case order), and both are written together. Reading the registry checks it against its schema and checks that the case file equals its rendering; any difference is a setup error. The registry renders with the fixture case file's timings, so a registry whose startup delay or settle time differs from the fixture case file's is a setup error too (a scenario would replay under timings it was not proven with), and so is naming the registry's own case file as the fixture case file, since discovery rewrites it. Discovery writes both into the working tree and never commits them; a person reviews and commits them. `npm start -- --case-file parity/cases/discovered.json` captures, compares, triages and diagnoses the registered scenarios like any case.

**Labels.** Each record gets an automatic `discovery` label once the run decides its outcome: a scenario record `proven`, `not-proven`, `invalid-plan`, `execution-failed` or `abstained`, with the number of differing captures when it executed; the rank record `proven` when one of its selected targets was proven, `not-proven` when one executed and none was proven, and `untested` when none executed. The label is automatic, never gold.

**The document and the exit status.** `conclude` writes `out/discovery/threads/<thread>/discovery.json`: the baseline thread, the source hash, the targets with their rank, each selected target's scenario (record, plan, validation reasons, case, execution outcome, visual outcome, proofs, admission) and the run's folder with its execution outcome (status, coverage valid, failures) apart from its visual result (rows passed and failed); the coverage before and after (the baseline's observed controls and exercised bindings, plus what the run proved); and the registry's entries before and after. It prints one line per scenario and a `Discovery:` line with the counts. The exit status is 0 when nothing below applies; 1 when an admitted scenario showed a finding; 2 when the capture run had status 2 or invalid coverage, or a job failed with `invalid_output` or `refused`; 3 for a setup error.

**Evaluation of both job kinds.** `jobKinds` gains `rank` and `scenario`, so the profile chooses their agent (default Claude, effort medium) and the store keeps their records under `eval-record/rank` and `eval-record/scenario`. `freeze --job rank|scenario` freezes one item per context of the succeeded workflow records that have a `discovery` label and whose context folder still exists, with copies of the context and the snapshot; a scenario item's gold is its proven plan (case and the tab names it selected) when its label is `proven`; a rank item's gold is the targets its threads proved and the ones whose scenario executed without proof where no thread proved them (a scenario that failed to execute says nothing about its target). Items are partitioned by target ID (rank items by context hash). `run` stages each item like a workflow job and scores `valid` (rank: the answer passed validation; scenario: its plan passes the validator against the context's fixtures, tab texts and labels; an abstention has no value, so abstaining neither passes nor fails it) and `reached` (rank: whether its best feasible target is among the proven ones, false when among the unproven or when it leaves no feasible target on an item whose gold has targets, else null; scenario: whether its valid plan uses the gold plan's fixture case and selects every tab name of the gold plan, null without gold). `compare` and `certify` accept those metrics for these runs and refuse the others; `compare` without `--metric` takes the first metric of the job kind. `npm run discover -- --unattended` starts only when `rank` and `scenario` have certificates for the thread's provider, model, effort and prompt version. The review queue, the grader, hindsight and the benchmark keep to hypothesis and challenge records.

## Risks / Trade-offs

- Most unobserved controls need a selected row or a dialog, which the four actions cannot do; the ranker may rightly call them infeasible, and a run may prove nothing. That is reported as such, never padded.
- A tab text the app sets at run time from another source than the language file is unknown to the validator, which then rejects a plan that would have worked. The validator stays strict; such a text can be added from a baseline tree once a case shows it.
- The registry's case names include the fixture file name, so renaming a fixture invalidates entries; the loader then fails on the missing fixture.
- Fixture tests prove targets, priors, validation, proof from synthetic trees, registry rules, routing and scoring; only live runs prove that models propose usable plans and that a scenario shows what the tree says.
