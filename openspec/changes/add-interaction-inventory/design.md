# Design

## Context

The capture runner (`visual-parity-capture`) opens each fixture in both executables, selects tabs, waits for labels and captures the main window; `npm start` (`parity-workflow`) captures, compares and triages every case and goes on to diagnosis and repair. The app's UI is declared in 69 WinForms designer files under `Chummer/`: 63 forms and 6 user controls, with about 1,300 event bindings written as `this.<control>.<Event> += new <Handler>(this.<method>);`. The character opens in `frmCreate` (build) or `frmCareer` (career) as an MDI child of `frmMain`; every other form is a dialog that opens from a menu, a button or a context menu. The cases' actions can only select tabs, wait and capture.

## Goals / Non-Goals

**Goals:**
- A source inventory of every form, control and event binding, derived from the source without hand curation.
- A scope that says, for every form and user control, whether the suite is expected to reach it, and why not when it is not.
- A coverage manifest built only from what a run proves: which controls were on screen in a capture, and which bindings an action provably raised.

**Non-Goals:**
- New action types, dialogs, value edits or new cases.
- Comparing the canonical side's UI tree with the candidate's; trees are recorded on the candidate side only.
- Event bindings made in code at run time (outside `InitializeComponent`); they are not in the inventory.
- Ranking or choosing what to cover next.

## Decisions

**The tree is recorded by the capture runner, on the candidate side, after the capture.** `IAppSession` gains `DescribeTree()`, which returns the nodes. `ChummerSession` builds a `CacheRequest` with the automation ID, name, control type, class name, enabled state, bounds and off-screen state, tree scope `Subtree` and tree filter `ControlView AND IsOffscreen = false`, fetches the main window's element with it once and walks its cached children. The result is a flat list of nodes in depth-first order, each with its parent's index, which keeps the contract free of recursion. The off-screen filter drops hidden tab pages and their thousands of controls. It skips an off-screen element but keeps its children that UI Automation reports on screen, so the tree also holds the children of a row scrolled out of its panel, outside the panel's bounds; the matching handles them (below). `SideExecutor` calls it right after a capture's bitmap is taken, before the image is saved and the capture is recorded (so a tree that cannot be read leaves no image of the failed capture), and writes the tree after the image, only when the run has `--ui-tree` and only on the candidate side; a tree that cannot be recorded fails the capture action with its reason, so the side fails and coverage is invalid. The timing decorator measures it as operation `uiTree`. The file is `ui-trees/<case>/<capture>.json` (`parity-ui-tree.schema.json`, title `UiTree`): run ID, case, capture, side and the nodes. The summary gets `uiTrees`, the folder relative to the run, absent without the option and, like the other documents' paths, when setup failed. *Why the candidate:* it is built from the source the inventory describes, it always runs live, and a canonical side restored from the cache carries no tree; the cache key and entries are unchanged. *Alternative:* a separate inventory executable; rejected because it would duplicate the launch, navigation and failure handling the runner already proves on every run.

**Automation IDs are WinForms control names.** UI Automation's proxy for WinForms windows reads `Control.Name` through `WM_GETCONTROLNAME`, so a node's automation ID is the designer field name of its control, and a user control created in code carries the name its designer sets (`this.Name = "SkillControl"`). Only WinForms windows (class `WindowsForms10.<class>.app.<n>.<hash>`) report a control name. Elements without a window of their own (tab items, tool strip and menu items, tree nodes) have no automation ID, and the parts of native controls (title bar buttons, scroll bar parts, a combo box's drop-down button and edit, list headers) have fixed UI Automation IDs such as `Close`, `Thumb` or `DropDown`. A window without a name (an `MdiClient`, the panels of a `SplitContainer`) gets its Win32 control ID, a number. So a node's control name is its automation ID only when it is a WinForms window and the ID is not a number; other nodes have none. Only a live run can show how many elements carry IDs; fixture tests cannot.

**The source inventory parses designer files.** `workflow/src/inventory/designer-parser.ts` reads each `*.Designer.cs` under `Chummer/` and `Core/` that has an `InitializeComponent` method. It recognizes, line by line:
- field declarations `<modifier> <Type> <name>;` as the class's controls and components;
- `this.<parent>.Controls.Add(this.<child>)`, `this.Controls.Add(this.<child>)` and the `Items.AddRange`/`DropDownItems.AddRange` lists as containment (a `SplitContainer`'s `Panel1`/`Panel2` belong to the `SplitContainer`);
- `this.<control>.Text = "…";` and `.Tag = "…";` (a string literal, joined with `+` over lines when the designer splits it) and `.ContextMenuStrip = this.<menu>;`;
- `this.Name = "…";` as the name the class gives its instances;
- `this[.<control>[.<member>]].<Event> += new <Type>(this.<method>);` as an event binding.

The code-behind (`<Class>.cs` beside the designer file) gives the base type (`partial class X : Form`) and the handler's line (`void <method>(`). The parser fails on an event binding it cannot read, a containment or binding naming an undeclared field, a missing code-behind, a handler that the code-behind does not define, a string assignment that is not made of string literals, or a string with an escape it does not read, naming file and line. Lines it does not need (layout, colours, resources) are ignored. Interactions get the ID `<Class>.<target>.<Event>`, with `(self)` as target for the class's own events. `source-inventory.json` holds the classes in name order with their controls and bindings, and its SHA-256 over the source files it read. *Alternative:* Roslyn; rejected because the designer code is generated and regular, and a Node workflow would need a .NET tool only for this.

**The scope file is explicit and complete.** `parity/inventory/scope.json` has `classes`, an object from class name to `{ "scope": "active" | "deferred", "reason": "…" }`, and `deferredEvents`, an object from event name to reason. Active: `frmMain`, `frmCreate`, `frmCareer` and the six user controls they host. Deferred: every dialog, with the reason that only a menu, button or context menu opens it and no case action can. Deferred events: lifecycle and layout events (`Load`, `Shown`, `Activated`, `FormClosing`, `Resize`, …) that no user action raises on purpose. A class missing from the file, a class the file names but the source lacks, an empty reason or an unknown scope is a setup error. *Why explicit:* a new form must be placed in or out of scope on purpose; nothing drops out of the denominator silently.

**Matching tree nodes to controls.** Each tree is walked from the root with a class context, initially none. A node is shown only when its parent is and its bounds overlap those of every WinForms window above it, since a window is clipped by its parents (an element that is not a window and has no rectangle is shown with its parent); a node that is not shown counts for nothing, with its subtree. A shown node whose control name names a control declared in the context class matches that control; when that control's type is an inventoried class, the context becomes that class for its subtree. Otherwise, when the control name is the instance name an inventoried class sets (`frmMain`, `frmCreate`, `SkillControl`, …), the node is an instance of that class and the context switches to it. Any other control name is unresolved and keeps its parent's context; nodes without a control name are not counted and keep their parent's context. A tab control's pages are `TabItem` children without IDs, named by their tab text, and the content of the shown page lies under its item: the page a tab control shows is the name of its one item with children and a name (an item without text shows no page), and that item matches the tab control's `TabPage` whose designer text is that name when exactly one has it (the app may change a tab's text at run time, as it does for `Initiation`). A matched control is `observed` in that case and capture.

**Exercised bindings need proof from consecutive captures.** For each case, the candidate side's performed captures are taken in action order. For two consecutive ones with at least one performed `selectTab` action between them, each tab control (a matched control of type `TabControl`) that shows a page in both trees, a different one by tab text in each, provably changed its selected page, so its bindings for `SelectedIndexChanged`, `Selected`, `Selecting`, `Deselecting` and `Deselected` are `exercised` in that case. Nothing else is exercised: a button on screen was not clicked. *Alternative:* counting every visible control's handlers; rejected because presence is not execution.

**The manifest.** `coverage-manifest.json` holds:
- the inventory's and the scope file's SHA-256, the runs it read (run ID, folder, candidate SHA-256);
- `tuples`: every planned case and capture with the candidate side's outcome from the run's coverage (`observed` for a performed capture, else `failed`, `filtered`, `missing`, `not-run`, `optional-absent` or `skipped-optional`) or `not-captured` when no run holds the case;
- `classes`: per class its scope and reason, and its counts of controls, observed controls, bindings and exercised bindings;
- `controls`: every control with its status (`observed` with the case and capture of each tree it was in, `unobserved`, `windowless` when its declared type is never a window and no tree matched it, or `deferred` with the class's reason);
- `interactions`: every binding with its handler, file and line and status (`exercised` with the cases and the two captures, `unexercised`, or `deferred` with the class's or event's reason);
- `unresolved`: per case and capture, the automation IDs that matched no control;
- `totals`.

Reading a run, a performed candidate capture without its tree, a summary without `uiTrees`, a case in two runs, a case no plan holds, or a document that does not match its schema is a setup error. The run's coverage validity does not filter anything: an observation in a tree is a fact of that capture even when a later action failed, and the tuple outcomes show the failures.

**The source must be the candidate's.** Only observations need this: without runs nothing is observed and no build is needed. In the workflow, the `inventory` node compares the compiled-source identity of the working tree (`Chummer/` and `Core/`) with the one the build recorded, with the same guard diagnosis uses (`requireRecordedSource` and `requireSameSource` beside the record), and stops with a setup error when they differ or none was recorded. `npm run inventory` does the same with the record beside `out/candidate/`, and also requires every run's candidate SHA-256 to equal the one the build recorded beside it, so a candidate from a plain `npm run build:candidate` is refused.

**Workflow integration.** The capture step passes `--ui-tree` and saves the tree files with its other outputs, so a reused step has intact trees; the step format version goes to 2, so records made before trees existed miss. Check, narrow, level and baseline captures do not record trees. The `inventory` node follows triage whenever triage runs (also with `--only triage`) and routes on as triage did; it writes `out/workflow/threads/<thread>/inventory/source-inventory.json` and `coverage-manifest.json` and the run's report prints, after the triage totals, `Inventory: <classes> classes (<active> active), controls observed <n>/<active controls>, interactions exercised <n>/<active interactions>, tuples observed <n>/<planned>, unresolved <n>`. A thread checkpointed before the node existed has no `inventorySummary` field and capture runs without trees, so the node does nothing for it and the report says the inventory did not run. The exit status is unchanged except for setup errors (3).

**`npm run inventory`.** `node --import tsx workflow/src/inventory/inventory-main.ts` with `--run <folder>` (repeatable), `--case-file`, `--scope` and `--out` (default `out/inventory/<UTC time>/`), and `--help`. Exit 0 when the documents are written, 3 for a setup error. Without `--run` every tuple is `not-captured`. Only the workflow's build records the candidate's source, so the command needs a candidate that `npm start` built; runs made with `npm run parity -- --ui-tree` against it qualify.

## What fixture tests prove and what only a live run proves

Fixture tests prove the parser on small designer and code files and on the repository's own designer files (every class parses, every handler resolves), the scope checks, the matching and exercise rules on synthetic trees, the manifest's statuses and errors, the tree recording through a scripted session, the summary and contract shapes, and the graph routing. Only a live run proves that UI Automation exposes the controls' names as automation IDs in this app, that the off-screen filter keeps what the capture shows, how long recording takes, and the real coverage numbers.

## Risks / Trade-offs

- Elements without their own window carry no control name, so menu and tool strip items and tree nodes are not counted as observed controls even when visible. The manifest lists the controls among them that are windowless by type (see below) apart and the others as unobserved rather than guessing from names; only a tab page is matched by its text, and only when the text names one page of its tab control.
- The tree is read right after the bitmap is taken, not at the same instant, so a repaint between the two shows in one only; the tree describes the app just after the capture.
- A child of a window the off-screen filter skipped keeps the context of the window above, because the skipped window is not in the tree. When it overlaps that window's bounds it is shown, and its name is listed as unresolved (or, if the window above's class declares the same name, matched there). The clipping keeps this to controls on the edge of a scrolled panel.
- The inventory lists every field a designer declares, including components that are never windows (tool tips, timers, image lists, menu and tool strip items, pop-up menus, dialogs, grid columns). A fixed list of such declared types marks a control no tree matched as `windowless`, which the totals of controls to observe leave out, so the observed share can reach all of what a tree can show. A type the list does not know counts as observable and stays `unobserved`, so an unlisted component overstates the gap rather than hiding one.
- Recording a tree adds time to every candidate capture; `timing.json` measures it.
- `bin/ChummerGenSR4.exe` is never rebuilt, replaced or written; the live run records its SHA-256 before and after, as every capture run does.
