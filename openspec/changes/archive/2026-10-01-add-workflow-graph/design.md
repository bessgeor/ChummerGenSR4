# Design

## Context

The capture runner (`visual-parity-capture`) runs selected cases on the canonical and the candidate executable and writes a run folder under `out/runs/<runId>/` with `summary.json`, `results.json`, `coverage.json` and `timing.json`; it exits with 0, 1, 2 or 3 and can report its run folder through `--run-folder-file`. The comparer (`visual-parity-compare`) analyzes one run folder in place, writes `compare/report.json` with discrepancies, duplicate groups and completeness, and exits with 0, 1, 2 or 3. A full suite takes about forty minutes live and about half of that when the canonical sides come from the cache.

## Goals / Non-Goals

**Goals:**
- One entry point (`npm start`) that runs build, capture, compare and triage as a LangGraph graph whose progress survives a crash, a kill or Ctrl+C.
- Never repeating a host step whose inputs and outputs are unchanged, and being able to force a capture again.
- Comparing case *k* while case *k+1* is captured.
- At most one desktop-driving process per machine, across worktrees.
- Discrepancy clusters across cases with an identity that stays the same across runs.
- The canonical capture cache on by default and shared by every worktree on the machine.
- A CI job that checks what can be checked without a desktop.

**Non-Goals:**
- Changing what capture or compare do, their contracts or their exit statuses.
- Running capture on CI (it needs an interactive desktop and the canonical executable's environment).

## Decisions

**A workspace with ports and a composition root.** `workflow/` is an npm workspace of the root package (`"workspaces": ["workflow"]`), TypeScript run with `tsx`, type-checked with `tsc --noEmit`. Graph nodes depend on small ports (`HostRunner`, `StepStore`, `ToolPaths`, the LangGraph checkpointer and store); `src/main.ts` is the composition root that wires the real adapters, and tests wire fakes. The generated zod contracts under `contracts/generated/typescript/` are imported to read case files and compare reports, so the workflow reads exactly the documents the .NET tools write.

**Graph.** The state holds the resolved options, the planned cases, the build's fingerprints, one outcome per captured case and one per compared case (both merged by case name), and the triage summary. Nodes:
- `build`: builds the candidate (`parity/scripts/build-candidate.mjs`, unless `--only` is `compare` or `triage`) and the capture runner and the comparer with `dotnet build -c Release`, all in the CPU pool. The candidate shares no project with the tools, so it builds beside them; the two tools build one after the other because they share projects. It then fingerprints the inputs every step key needs (below).
- `capture`: runs one case, addressed by its index through `Send`.
- `compare`: compares one captured case, addressed the same way.
- `triage`: runs once every planned case is compared.

After `build`, a conditional edge sends `capture` for the first case. After `capture` *k*, it sends `compare` for *k* and, when there is one, `capture` for *k+1*; both run in the same LangGraph super-step, so compare *k* overlaps capture *k+1*. After `compare`, the edge goes to `triage` only when every planned case has a compare outcome, else nowhere. *Alternative:* one node that runs capture and compare concurrently with promises; rejected because the checkpointer could not see either step's progress.

**Checkpoints and threads.** `SqliteSaver` from `@langchain/langgraph-checkpoint-sqlite` stores checkpoints in `out/workflow/checkpoints.sqlite`. A new run gets the thread ID `wf-<UTC timestamp>-<8 hex>`, printed at the start with the resume command. `--resume <thread>` invokes the graph with `null` input on that thread, so LangGraph continues from its last checkpoint; it accepts no other options, because the thread's state already holds them. A thread that does not exist, or one that has finished, is a setup error. A step that did not finish before the process stopped runs again on resume, and the step store below makes that cheap when it had completed.

**Idempotent host steps.** A step's key is the SHA-256 of key lines, which are kept in its record:
- capture: the step format version; the case's character entry, its expanded actions in order, and the case file's startup delay and settle time; the fixture's SHA-256; the environment fingerprint (below); the capture names it is limited to, or `*`; the threshold; the canonical executable's SHA-256; a fingerprint of the canonical support files the stager copies (`data`, `lang`, `settings`, `sheets`, `export`, the two manifests); a fingerprint of the candidate folder's files; a fingerprint of the overlay or `none`; `canonical:cache` or `canonical:live`; a fingerprint of the capture runner's `Parity.*.dll` files. A capture step also checks, after the runner exits, that its `coverage.json` lists only the planned case: the runner matches `--case` against case names and also fixture file names, so a name can select a second case, and a run that covers more than the planned case is a setup error and is not recorded.
- compare: the step format version; the capture step's key and the SHA-256 of the capture run's `results.json` and `coverage.json`; `--no-ocr`; a fingerprint of the contents of the `--tessdata` folder, or `default`; a fingerprint of every file in the comparer's output folder except debug symbols, which covers its assemblies, the OCR engine's libraries and the default language data.

A fingerprint is the SHA-256 over every file's relative path and SHA-256, ordinally sorted. A completed step writes `out/workflow/steps/<kind>/<key>.json` (written to a temporary file and renamed) with the key lines, the run folder, the exit status, the thread, the time and the SHA-256 of its outputs (`summary.json`, `results.json`, `coverage.json` and every screenshot under `captures/` for capture; `compare/report.json` for compare). A later step with the same key reuses the record only if every recorded output still has its hash; otherwise it runs the step again and says why. `--recapture` skips the lookup of capture steps (`--only compare` and `--only triage` do not run capture and reject it) and records the new run under the same key, so a difference that came from a paint race can be collected again without deleting files by hand. Only steps that ended with status 0 or 1 are recorded: a step with execution failures or analysis failures (2) is evidence of a problem that must be collected again, not reused. A setup error (3) is never recorded. The build node's fingerprints are recomputed by each step for the inputs it depends on, and a difference is a setup error ("inputs changed since the thread started"), so a resumed thread never mixes candidates or tools: a capture step checks the canonical executable, the stat fingerprint of the canonical support files (sizes and modification times, so the whole tree is not hashed again for every case), the candidate, the overlay and the capture runner's assemblies; a compare step checks the comparer's assemblies.

**Environment fingerprint.** What decides the pixels besides the files above is the machine: the screens and their per-monitor scale, the system scale, the OS build and patch level, the cultures, the Windows colour, theme, font smoothing, window metric, text scale and high contrast settings, and the app's own options in the registry. The capture runner already reads exactly these lines to key its canonical cache; its option `--environment-fingerprint-file <path>` writes their SHA-256 to the file and exits with 0 without running a case, so the workflow does not reimplement the list. Each capture step reads it, in the CPU pool, before it looks its key up, so a step recorded at 100 % scaling is not reused at 125 %. *Alternative:* trusting the checkpoint alone; rejected because a step interrupted in the same super-step as a failure is not in the checkpoint, and because a new thread should reuse what an earlier thread produced.

**Tools run as built assemblies.** Capture and compare run as `dotnet <project>/bin/Release/net10.0/<Project>.dll` from the repository root, not through `dotnet run`, so the two concurrent steps never build. Capture is passed `--case <name>`, `--run-folder-file <file>`, `--repo-root`, the capture filter, the threshold, the case file, the overlay and the cache folder; compare is passed `--run <folder>` and the OCR options. The run folder file lives in a temporary folder that is removed afterwards. A compare step's status counts only when `compare/report.json` exists and its status matches the exit status (`clear` 0, `differences` 1, `analysis-failures` 2), as before.

**Host runner, lane and pool.** `HostRunner.run({ resource, label, command, args })` acquires the resource, starts the child with the repository root as working directory, prefixes each output line with the label, waits for the exit and releases the resource. A child that cannot start, or ends from a signal, is a setup error. A command may carry an abort signal: LangGraph aborts the nodes of a super-step when one of them fails, and the host runner then kills the child and everything it started (`taskkill /t /f` on Windows) and reports a setup error, so the capture runner of case *k+1* does not keep driving the desktop after the compare of case *k* ended with 3; a command whose signal has already aborted is not started. If releasing the lane fails after the child failed, the child's error is the one reported and the lock problem is printed beside it; if the child succeeded, the lock problem is the error. Ctrl+C (SIGINT) aborts the same way: `main.ts` aborts the signal it gives the graph, the running children and their descendants are killed (the Chummer windows a capture started included), the lane is released, and the run ends with status 3 and the resume command, with the first Ctrl+C only; a second one ends the process at once. Closing the console window (SIGHUP) and Ctrl+Break abort the same way. Ctrl+C also reaches the capture runner, which can end before its process tree is killed and then leaves the apps it started running, out of reach of the tree kill; so the abort of a desktop command also stops every process whose executable lives under `out/runs`, where a capture stages the apps it drives. If stopping those apps fails (PowerShell missing, for example), the error is printed beside the interruption and the run still ends as interrupted with status 3 and the resume hint, because nothing more can be done at that point; the printed error names what may still be open, and a resumed capture would fail with a `window-activation` reason if such a window took the foreground. The build commands carry the same abort signal, so an interrupt also stops a running MSBuild or `dotnet build` and their children.
- `desktop`: a lock file at `<local app data>/ChummerGenSR4/desktop-lane.lock`, created with exclusive create and holding the host name, process ID, start time and a random owner token. If it exists, the runner reads it: a running owner is waited for, polling every two seconds and printing once whom it waits for; a lock that stays unreadable for ten seconds is a setup error naming the file. A lock of this host whose process is no longer running (`process.kill(pid, 0)` gives `ESRCH`) is taken over under a guard file `desktop-lane.lock.takeover`, created with exclusive create: while holding it the runner reads the lock again and removes it only if it still holds the token it judged abandoned, so a waiter that read the same dead owner a moment later cannot remove the live lock of the run that took over first; then it retries the creation. A guard that stays for ten seconds is a setup error naming it. Process IDs are reused, so the owner also refreshes the lock file's modification time every ten seconds while it holds the lane, and a lock of this host that has not been refreshed for ninety seconds is abandoned even if a process with its ID exists; the takeover then says so. Waiting for a lane, and waiting for a takeover guard, end when the command's abort signal aborts. A refresh that fails is printed (again every ten seconds while it keeps failing) and the capture goes on: stopping a capture that is driving the desktop would lose its work for what is usually a transient file-system error. The cost is that after ninety seconds without a refresh another run may take the lane over while this capture still runs; the printed errors are the evidence of that. Release removes the file only if it still holds the runner's token.
- `cpu`: a counting semaphore inside the process, sized by the profile's `cpuPool` or half the logical processors (at least 1, at most 4).

**`--only <node>`.** `capture`, `compare` or `triage`. Nodes before it run in reuse-only mode: a step without a valid record is a setup error that names the case and says to run the earlier node first. Nodes after it do not run. The build node always builds the tools, because the keys need their fingerprints, and builds the candidate only for `--only capture`.

**Cases and options.** The workflow loads the case file with the generated `ParityCasesSchema`, derives each case's name as the capture runner does (`<mode>-<fixture name without extension>`), and selects cases with the runner's rules (case name, file name or file name without extension, case-insensitive; an unmatched name is a setup error). It expands each case's actions (with `include` sequences) to know its capture names; with `--capture`, each case is passed the subset it has, a case with none of them is left out of the plan with a printed line, and a name no case has is a setup error. Capture options `--case`, `--capture`, `--settings-overlay`, `--threshold` and `--case-file` and compare options `--no-ocr` and `--tessdata` are accepted; `--canonical-exe`, `--candidate-exe`, `--runs-dir`, `--run-folder-file` and `--repo-root` are set by the workflow and rejected; any other option is a setup error.

**Byte-identical tool builds across checkouts.** The capture runner's cache key and the workflow's step keys include the hashes of the tools' assemblies, so a machine-wide cache only hits across worktrees if every checkout compiles the same bytes. The tools already build without commit IDs and with the repository root mapped to a fixed path; the remaining difference is line endings, which follow each checkout's `core.autocrlf` and any tool that rewrites a file. `parity/.gitattributes` and `contracts/.gitattributes` therefore pin `eol=crlf` for the C# sources, project files, props, targets and the solution, and the contract generator writes the generated C# with CRLF. `contracts:check` compares generated C# byte for byte, so C# written with LF is reported as stale (it would compile to a different assembly while Git still shows the file as clean under `eol=crlf`); generated TypeScript is compared ignoring line endings, because a checkout may convert them. *Alternative:* normalizing line endings inside the key; rejected because the key hashes the compiled assemblies, not the sources.

**Canonical cache and profile.** The cache folder is `--canonical-cache <dir>`, else `PARITY_CANONICAL_CACHE`, else the profile's `canonicalCache`, else `<local app data>/ChummerGenSR4/canonical-cache`; `--live-canonical` omits the cache. The local profile is an optional JSON file at `PARITY_WORKFLOW_PROFILE` or `<local app data>/ChummerGenSR4/workflow-profile.json` with `canonicalCache`, `settingsOverlay` and `cpuPool`, validated strictly; an invalid file is a setup error. The capture runner still checks that the cache folder is outside the repository or under `out/`.

**Triage clusters and identity.** Triage reads each case's `compare/report.json` with `CompareReportSchema`. It walks the discrepancies in plan order and report order and puts each into the first cluster whose representative has the same image hash and a core position match of at least 97 % (the comparer's rule, now across cases; the capture size comes from the discrepancy's row). Each cluster's identity is looked up in the LangGraph store under the namespace `["discrepancy", <image hash>]`: a stored identity whose core matches the representative at 97 % or more is reused, as known unless the thread itself stored it (a triage that stored its identities and then stopped before it wrote `triage.json` runs again on resume, and its identities are still new); otherwise a new identity `d-<first 16 hex of SHA-256 of "<image hash>:<x>,<y>,<width>,<height>">` is stored with the core, the capture size and the thread that first saw it. The store is a small `BaseStore` implementation over SQLite in `out/workflow/store.sqlite` that supports `get`, `put` and prefix `search`; `listNamespaces` and semantic search throw. Rows whose status is `failed`, `size-mismatch`, `missing-canonical` or `missing-candidate`, and completeness entries that are `execution-lost` or `unaccounted`, are listed under `otherFindings`, never dropped. `out/workflow/threads/<thread>/triage.json` holds the per-case capture and compare outcomes (status, run folder, whether the step was reused), the clusters with their members and crops, the other findings, and totals; it is validated with a zod schema before it is written. A case's `canonicalSource` is `cache` when every canonical side came from the cache, `live` when none did and `mixed` otherwise. The comparer replaces `compare/` in the capture's run folder, which another thread may share, so before it reads the reports triage checks that every compare step's record (status 0 or 1) is still valid, which includes the report's hash; a report another run replaced is a setup error that says to run the compare step again. A report that cannot be read is a setup error.

**Exit status.** The highest capture and compare status of all planned cases (0, 1 or 2); 3 for a setup error, which includes a failed build, a capture or compare exit status of 3, a compare status that does not match its report, an unreadable report, a lock that cannot be verified and invalid options. A setup error ends the run at once, prints the thread to resume, and leaves the thread resumable. When the graph ends, the workflow reads each planned case's run folder (`coverage.json`, `results.json` and, for a compared case, `compare/report.json`, through the generated zod schemas, so a document that does not match is a setup error) and prints two lines per case, also with `--only`: the execution line (capture status and where it came from, coverage validity and its reasons, whether every side's action indexes are contiguous, the number of failures and optional absences, and whether the canonical side came from the cache, was live or both) and the visual line (results passed and failed, compare status, the report's status, discrepancies, groups and completeness counts). The triage totals follow.

**CI.** `.github/workflows/ci.yml` runs on pushes and pull requests on `windows-latest`: Node 22 (the root package requires Node 22 or newer, because the test scripts pass glob patterns to `node --test`), .NET 10, `npm ci`, `npm run workflow:typecheck`, `npm run workflow:test`, `dotnet build parity/Parity.slnx -c Release` and `npm run contracts:check`.

## What fixtures prove and what only a live run proves

- **Unit tests prove** (fake host runner, temporary folders, in-memory or temporary SQLite): the node order and the overlap of compare *k* with capture *k+1*; the exit status rules; resume after a failing step continuing at that step without repeating completed ones; step reuse, a changed output forcing a re-run, status-2 steps not being recorded; `--only` reuse-only failures and skipped nodes; option parsing and rejection; case selection and capture subsets; the cache folder precedence and `--live-canonical`; the lane lock's wait, stale takeover, takeover guard and token check; aborting a child, not starting one after an abort, and a child ended by a signal (with a fake process); the capture key changing with the environment fingerprint, `--recapture`, tool and app changes during a thread, screenshots in the recorded outputs, a replaced compare report; the per-case report lines; the contract drift check on LF C#; the CPU pool's bound; triage clustering across cases, identity reuse across threads and for shifted cores, new identities, other findings; the store's operations.
- **Only a live run proves:** that the real tools run as built assemblies from the graph, that compare overlaps capture on the real suite, that the canonical sides come from the machine-wide cache by default and run live with `--live-canonical`, that a really interrupted run resumes, that triage's clusters match the comparer's groups on real reports, and that the canonical executable's hash is unchanged.
- **Only CI proves:** that the job passes on a clean GitHub-hosted Windows runner.

## Risks / Trade-offs

- [A super-step waits for its slower node] → compare of a case usually takes less time than capturing the next, so the overlap is close to the ideal; the last compare runs alone.
- [The lock file outlives a killed process] → the owner's process ID is checked; a reused process ID keeps the lock until that process ends, which only delays the run.
- [A step key misses an input] → the capture runner's own cache key and coverage audit still apply inside each step; the key includes the tools' assemblies, so a tool change misses.
- [Per-case runs stage the apps once per case] → staging takes a few seconds per case against minutes of capture.

## Migration Plan

Additive for the tools. `npm start` keeps its exit statuses and pass-through options, gains `--resume`, `--only` and `--live-canonical`, and now writes one run folder per case. Rolling back means reverting the change's commits; `out/workflow/` holds only disposable state.
