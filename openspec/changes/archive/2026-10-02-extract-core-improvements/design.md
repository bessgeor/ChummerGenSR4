# Design

## Context

`Chummer/clsImprovement.cs` holds two types. `Improvement` is a plain record of one bonus with its two enumerations and its save and load code; it uses nothing but `System.Xml`. `ImprovementManager` (about 2,000 lines) is created with a character at 40 places in the app, three of them with `null` for gear inside vehicles, and is used through `CreateImprovements`, `CreateImprovement`, `RemoveImprovements`, `Commit`, `ValueOf`, `LimitSelection`, `ForcedValue` and `SelectedValue`. Outside the library it uses:

| What | Members |
|---|---|
| `Character` | `Improvements`; the flags `MAGEnabled`, `RESEnabled`, `MagicianEnabled`, `AdeptEnabled`, `TechnomancerEnabled`, `CritterEnabled`, `InitiationEnabled`, `BlackMarket`, `Uneducated`, `Uncouth`, `Infirm` (read and set) and `AdapsinEnabled` (read); `InitiateGrade` and `SubmersionGrade` (read and set); the attributes `BOD` to `RES` (`TotalValue`) and `GetAttribute` (`MetatypeMaximum`); `Skills` (`Name`, `Specialization`); `Weapons` (`Name`, `DisplayName`); `Cyberware` (the Adapsin grade conversion) |
| Windows Forms | `frmSelectText`, `frmSelectItem` (restricted items, sprites, weapons), `frmSelectSkill`, `frmSelectSkillGroup`, `frmSelectAttribute` (two uses), `frmSelectSpell`, `frmSelectMentorSpirit` (mentors and paragons), `frmSelectSide`; `DialogResult`; the window's `Opacity` set to 0 to take a forced value without showing the window |
| Equipment | `GradeList` and `Grade` in the Adapsin grade conversion |

It also reads `LanguageManager`, `GlobalOptions` and `XmlManager`, which the library already holds. The library reaches the application through `IApplicationHost`, registered once in `ApplicationHost.Current`, and `IMainForm`. The parity workflow already treats `Chummer/` and `Core/` as the compiled source.

## Goals / Non-Goals

**Goals:**
- `Improvement` and the whole `ImprovementManager` in the library, with their git history, unchanged in what they do.
- The app behaving and looking exactly as before, including every selection window a bonus opens.
- Every type defined once across the executable and the library; no call site of the manager changes.
- The manager runnable without the application, so its logic can be tested.

**Non-Goals:**
- Moving the character, the attributes, skills, weapons or cyberware, or changing the selection windows.
- Changing the moved code beyond what reaching the application through interfaces requires: no renames of the manager's members, no cleanup of its logic.
- Touching the canonical `bin/ChummerGenSR4.exe`.

## Decisions

1. **A character interface that mirrors the members the manager uses.** `IImprovementCharacter` declares exactly the members of the table above with the same names and types, except where the type is an app type: `GetAttribute` returns an `IImprovementAttribute` (`TotalValue`, `MetatypeMaximum`), `Skills` an `IEnumerable<IImprovementSkill>` (`Name`, `Specialization`) and `Weapons` an `IEnumerable<IImprovementWeapon>` (`Name`, `DisplayName`). `Character` implements the three members whose types differ explicitly, by returning its own `GetAttribute`, `Skills` and `Weapons`, and every other member implicitly; `Attribute`, `Skill` and `Weapon` implement their views implicitly, so their code does not change. The manager's attribute arithmetic reads `GetAttribute("BOD")` and so on instead of the eleven attribute properties, which return the same objects. The manager's field and constructor take an `IImprovementCharacter`, so the 40 call sites, including `null`, compile unchanged. The small views sit in the character interface's file, since they exist only for it.
2. **The Adapsin grade conversion moves onto the character.** It walks the character's cyberware and replaces each Adapsin grade with the grade of the same name without `(Adapsin)` from `GradeList.BiowareGrades` or `GradeList.CyberwareGrades`, which are equipment types. `Character.ConvertAdapsinGrades()` holds that loop unchanged, the interface declares it, and the manager calls it where the loop was, under the same condition (the last Adapsin improvement removed and `AdapsinEnabled` false).
3. **One dialogs interface that asks for a selection.** `IImprovementDialogs` has one method per selection: `SelectText`, `SelectRestrictedItem`, `SelectSkill`, `SelectSkillGroup`, `SelectAttribute`, `SelectSwapSkillAttribute`, `SelectSpell`, `SelectMentorSpirit` (mentor spirits or, with `paragons.xml`, paragons; it returns a `MentorSpiritSelection` with the mentor, its bonus node and the two choices with their nodes), `SelectSide`, `SelectSprite` and `SelectWeapon`. Each takes what the manager decided (the friendly name, the forced or limiting value, the lists and filters it read from the bonus node, the character where the window needs one) and returns the selected value, or `null` when the user cancelled. The manager keeps every decision of what to ask and what to do with the answer; the app's `WinFormsImprovementDialogs` keeps everything about the window: the description texts from the language file, setting `Opacity` to 0 for a forced value, the order of the calls that build the attribute list (adding `MAG` and `RES`, limiting, then removing for a selected attribute; removing, then limiting for a swapped skill attribute), and the cancel check, which for the side window is made whether or not the window was shown, as before. A window that needs the character (restricted items, skills, spells, mentor spirits) gets the `Character` the manager was given, by a cast that throws for any other implementation of the interface, so a wrong character cannot pass unnoticed. A per-window interface that the forms implement was the alternative; it would have kept `Opacity` and dialog results, which are window details, in the library's code.
4. **The host gives the dialogs.** `IApplicationHost` gains `ImprovementDialogs`, and `WinFormsApplicationHost` returns one `WinFormsImprovementDialogs`. The library keeps one registration point, which already throws when nothing is registered.
5. **Two constructors.** `ImprovementManager(IImprovementCharacter)` is the one the app uses: it takes the host's dialogs and loads the selected language as before. `ImprovementManager(IImprovementCharacter, IImprovementDialogs)` takes the dialogs it is given and reads neither the host, the language nor the options; since the description texts now come from the app's dialogs, the manager's own code needs none of them. A value that contains `Rating` or an attribute name is evaluated as an expression, and the result is formatted and read back in a fixed `en-US` culture, the culture `GlobalOptions.CultureInfo` always holds, so that no bonus reaches the options, whose static constructor reads the host. The former code formatted the result in the culture of the thread and read it as `en-US`, so on a machine with a decimal comma a fractional result such as `1,5` was read as 15; formatting it in the same culture ends that, and is the one deliberate change of behaviour of this change. A sprite selection still loads `critters.xml` through `XmlManager`, which needs the host. Tests use the second, so they share no process-wide state with the host's test and do not depend on the order in which tests run.
6. **Move order.** The character interface names `Improvement`, and the dialogs interface names the character interface, so neither can be in the library before `Improvement` is. Each step builds and keeps the app's behaviour, and the move is a commit of its own:
   1. still in the app, as `Chummer/IImprovementCharacter.cs` and `Chummer/IImprovementDialogs.cs`: the interfaces, without any Windows Forms type; the app's dialogs and the implementations on `Character`, `Attribute`, `Skill` and `Weapon`;
   2. in place, still in `Chummer/clsImprovement.cs`: the manager reaches the character and the windows only through the interfaces, and the Adapsin loop moves onto the character; until the host can give the dialogs, the app's constructor creates a `WinFormsImprovementDialogs`;
   3. `Chummer/clsImprovement.cs`, `Chummer/IImprovementCharacter.cs` and `Chummer/IImprovementDialogs.cs` moved together to `Core/Improvement.cs`, `Core/IImprovementCharacter.cs` and `Core/IImprovementDialogs.cs`; `IApplicationHost` gains `ImprovementDialogs`, and the moved constructor takes the host's dialogs instead of creating them. Besides that line, the move commit only drops the `using System.Windows.Forms;` line of `clsImprovement.cs`;
   4. after the move, a commit of its own for the culture of the values of expressions (see 5), so that the behaviour change is not hidden in the rename.
   Preparing in place first keeps the move commit a nearly pure rename of a 2,800-line file. Both types stay in one file, as before, so the whole history follows one path. The moved file keeps its BOM and CRLF line endings; new files are stored with CRLF like the other source files.
7. **The workflow does not change.** Its compiled source already covers `Chummer/` and `Core/`, and its prompts already describe both, so no prompt version changes.

## Risks / Trade-offs

- **A selection window configured differently.** A wrong description, a missing forced value or a different list order would change what the user picks from. Mitigation: each dialogs method is the former block with the manager's fields replaced by its parameters, in the same order; the in-place commit is reviewed as that one-to-one replacement before the move.
- **No case opens a selection window.** The capture cases open saved characters, whose improvements are loaded from the file, so the live run does not create improvements through a selection. Mitigation: unit tests run the moved manager's selections with test dialogs (the forced and cancelled paths, the rollback, removal and the flags) and its value arithmetic; the windows themselves remain unverified live.
- **A value read differently on a machine with a decimal comma.** Formatting the result of an expression in `en-US` changes the value of a fractional result on such machines (15 before, the rounded-down value now). Mitigation: a unit test runs a fractional value on a thread with a Russian culture; the capture machine uses `en-US`, so the live run does not show the change.
- **The character interface grows with the manager.** It names exactly what the manager uses today; a new use would add a member.

## Verification

Fixture-tested (no desktop): the candidate build; a listing of the types of the executable and the library compared with a build of the source before this change; the rename similarity of the move commit; the C# tests of the moved manager with a test character and test dialogs, and the host test with the new member.

Only a live run proves that the app starts, opens every case's character with its improvements and draws every captured window as the canonical executable does: `npm start` over the whole case suite with diagnosis, repair and widening, recording the canonical SHA-256 before and after, execution outcomes apart from visual results, and the loop's outcome for any discrepancy.
