# Design

## Context

`Chummer/Chummer.csproj` is a ToolsVersion 4.0 project targeting `v4.0` with the `Client` profile. It lists every `Compile`, `EmbeddedResource` and `None` item, ClickOnce and bootstrapper settings that nothing uses, and the WCF metadata of two service references (`OmaeService`, `TranslationService`) whose endpoints under `chummergen.com` are gone. Its Release configuration writes `ChummerGenSR4.exe` into `..\bin\`, beside the canonical executable, which is why every build for comparison goes through `parity/scripts/build-candidate.mjs` with an overridden output and intermediate path. The machine build uses the MSBuild of Visual Studio (Build Tools), found by `vswhere`; no .NET Framework 4.8.1 Developer Pack is installed.

A build of the current project is the baseline: comparing its metadata with the canonical executable (types with their methods and fields, assembly references, manifest resources with the SHA-256 of their bytes, PE flags) shows no difference but the `DebuggableAttribute` flags, so any further metadata difference comes from this change.

## Goals / Non-Goals

**Goals:**
- An SDK-style project on `net481` that compiles exactly the sources and embeds exactly the resources the old project did, minus the removed service code, with the same assembly name, manifest resource names, entry point, icon and output folder.
- No code, configuration or reference that exists only for the Omae and Translation services.
- Candidate builds keep working for every caller of `build-candidate.mjs` (the candidate, diagnosis snapshots, repair attempts and widening builds), with sources outside the repository too.

**Non-Goals:**
- Moving code out of the app, changing behaviour other than the removed Omae feature, nullable or language-version changes, or other package upgrades.
- Building with `dotnet build`: the project builds with Visual Studio's MSBuild, as before.
- Touching the canonical `bin/ChummerGenSR4.exe`.

## Decisions

1. **Remove the services first, convert second.** The removal is done on the old project, so its effect can be measured alone: the metadata of the removal build differs from the baseline only by the deleted types (the `OmaeService` and `TranslationService` proxies, the Omae forms, `OmaeRecord`, `OmaeHelper`, `OmaeMode` and the Omae event handler delegates), their eight form resources, the changed `frmMain`, `frmUpdate` and `GlobalOptions` members and the four dropped assembly references. The SDK conversion is then measured against the removal build.
2. **Everything Omae goes, not only the proxies.** The Omae forms call the proxies on every action, so keeping them would mean keeping windows that can only fail. The `Tools > Omae` menu item opens them and goes too. `OmaeHelper` held the service factories plus compression helpers used only by the Omae forms, except `Decompress`, which the update window uses on downloaded data files; that one method moves into `frmUpdate` unchanged, and `OmaeHelper` is deleted. The Omae account options are read from the registry only for those forms and are removed; the registry values themselves are left alone. The language files keep `Menu_Main_Omae`, which the options and viewer windows use to label print sheets in an `omae` folder.
3. **SDK project with the old project's settings spelled out.** `OutputType` `WinExe`, `AssemblyName` `ChummerGenSR4` (`ChummerGenSR4_Debug` for Debug), `RootNamespace` `Chummer`, `StartupObject`, `ApplicationIcon`, `GenerateAssemblyInfo=false` (the project has `Properties/AssemblyInfo.cs`), `PlatformTarget` AnyCPU (the SDK would make a .NET Framework executable x86; its default of no 32-bit preference matches the old build), `WarningLevel` 4, `DebugType` `full`/`pdbonly`, and `OutputPath` `..\bin\` with `AppendTargetFrameworkToOutputPath=false`, so the Release output stays where it was and `build-candidate.mjs`'s `OutputPath` override still names the exact folder.
4. **Globbing with two guards.** Default `Compile`, `EmbeddedResource` and `None` globs replace the item lists; resources use the dependent-upon convention, which gives the same manifest names (`Chummer.<form>.resources`, `Chummer.Properties.Resources.resources`) as the explicit `DependentUpon` metadata did. `InheritedListView.cs`, which the old project never compiled, is removed from `Compile`. `obj\**` and `bin\**` under `Chummer/` are excluded explicitly, because candidate builds move the intermediate folder elsewhere and the SDK then no longer excludes a local `obj\` left by an IDE build. `settings\Darkness_in_the_heart_of_texas.xml` keeps `CopyToOutputDirectory=Always`.
5. **References.** The SDK adds the usual framework references for .NET Framework (`System`, `System.Core`, `System.Data`, `System.Drawing`, `System.Xml`, `System.Xml.Linq`, `Microsoft.CSharp` and others); the project adds `System.Windows.Forms` and `System.Windows.Forms.DataVisualization`. The compiler only records references the code uses, so the assembly's references stay those of the removal build.
6. **Reference assemblies from a package.** `Microsoft.NETFramework.ReferenceAssemblies` 1.0.3 (`PrivateAssets=all`) supplies the net481 reference assemblies, so neither a Developer Pack nor a particular .NET SDK version is needed; it adds no file to the output. Hence `build-candidate.mjs` passes `-restore` to MSBuild. Restore writes its assets file into the intermediate folder the script already sets, so a build from a source copy outside the repository leaves that copy and the repository untouched; the package itself is read from, or added to, the user's NuGet cache. Restore failures are build failures (exit 1), like any other MSBuild error.
7. **No preserialized resources.** Visual Studio's MSBuild runs on .NET Framework and embeds the forms' bitmaps and icons the classic way, as the old project did, so the project does not set `GenerateResourceUsePreserializedResources` and adds no `System.Resources.Extensions` dependency. The metadata comparison shows identical resource bytes.
8. **`app.config` asks for 4.8.1.** The SDK writes `app.config` to the output as `ChummerGenSR4.exe.config`, as the old project did, and `supportedRuntime` names `.NETFramework,Version=v4.8.1`, matching the target.
9. **Legacy accessibility behaviour.** .NET Framework turns its Windows Forms accessibility improvements on by the target framework of the executable: an app targeting 4.8.1 gets all of them, one targeting 4.0 none. They change rendering, not only the accessibility tree: with them, the character window intermittently drew a dotted focus rectangle on the selected "Other Info" tab after the full build scenario of one character, which the canonical executable never does. `app.config` therefore sets `Switch.UseLegacyAccessibilityFeatures`, `.2`, `.3`, `.4` and `.5` to `true` in `AppContextSwitchOverrides`. All five are needed: the framework's `System.Windows.Forms` has five levels (`AccessibilityImprovements.Level1` to `Level5`), and it refuses, with a `NotSupportedException` from the first tool strip at startup, a configuration that turns off a lower level while a higher one stays on. The improvements stay off in this change; turning them on would be a visual change of its own.

10. **Rider's MCP server across checkouts.** The built-in MCP server of Rider is measured on scratch copies of `Chummer/` and the solution, outside any checkout: its endpoint, the tools it lists, whether refactorings in two projects run at the same time, and what each additional project or process costs in memory. The result is a developer note, `docs/rider-mcp.md`; no code of the app or the tooling depends on it. Scratch copies keep every checkout untouched.

## Risks / Trade-offs

- [The `TargetFrameworkAttribute` changes from 4.0 Client to 4.8.1, which switches on .NET Framework behaviour that is keyed on the target] → identical IL and resources cannot show this; only the live run of every case on both executables can. The accessibility improvements are switched back (decision 9); a difference the live run finds is a regression of this change, reported as such.
- [Some target-keyed differences are intermittent, like the focus rectangle, and appear only after a full scenario] → a single clean run does not prove their absence; the evidence for decision 9 is repeated full runs of the affected case with and without the switches, and the final run covers the whole suite.
- [A machine without .NET Framework 4.8.1 refuses to start the app] → 4.8.1 is the stated target of the modernization; the verification machine has it.
- [`-restore` needs the package in the NuGet cache or a feed] → the package is fetched once; a missing feed fails the build with MSBuild's error and exit 1, never a silent fallback.
- [Removing the Omae menu item changes the Tools menu] → no parity case opens that menu; the change is listed in the proposal as breaking.

## What tests prove and what only a live run proves

- Fixture and build checks prove: the project restores and builds through `build-candidate.mjs`, from the repository and from a copy outside it; the Release configuration evaluates its output to `bin\ChummerGenSR4.exe`; and the assembly metadata (types, members, references, resources and their bytes) matches the removal build apart from the target framework.
- Only a live run proves that the rebuilt app behaves and looks like the canonical executable: `npm start` over the whole case suite, with the canonical SHA-256 recorded before and after, execution outcomes (capture status, coverage) reported apart from visual results, and any discrepancy handled by the workflow's diagnosis, repair and widening.
