# Design

## Context

`Chummer/clsEquipment.cs` (about 16,000 lines) holds `CapacityStyle`, the unused `Equipment`, `ArmorMod`, `Armor`, `Grade`, `GradeList`, `Cyberware`, `Weapon`, `WeaponAccessory`, `WeaponMod`, `LifestyleType`, `Lifestyle`, `Gear`, `Commlink`, `OperatingSystem`, `VehicleMod` and `Vehicle`. The armor, cyberware and gear types (lines 12–2071, 2073–4175 and 9494–13300, about half of the file) use, besides the library's data, options, language and improvement classes, these types of the app:

| What | Where |
|---|---|
| `Character` | the field and constructor of every type, the `Create` parameter of `Cyberware`, `Gear`, `Commlink` and `OperatingSystem`, and `Gear.CreateChildren`. The members read are `Options`, `Created`, `Improvements`, `Metatype`, `MetatypeCategory`, `CHA`, `INT`, `LOG` and `WIL` |
| `TreeNode` | the `Create` methods set the node's `Text` and `Tag`, create child nodes (the mods and gear of an armor, the subsystems of a cyberware, the children and plugins of a gear), add them with `Nodes.Add`, `Expand` the node, and colour weapon and subsystem nodes with `SystemColors.GrayText`; the `Copy` methods of the gear types do the same for the copied children |
| `ContextMenuStrip` | `Armor.Create` gives the nodes of included mods the context menu of armor mods |
| `Weapon` | `ArmorMod`, `Cyberware` and `Gear` create the weapons they grant on a new grey node and add both to two lists the caller passes; `Gear` renames an aerodynamic grenade's weapon and sets its range |
| `frmSelectNumber` | `Armor`, `Cyberware` and `Gear` ask for a variable cost in a window that cannot be cancelled |
| `frmSelectWeaponCategory` | `Gear` asks for the weapon category of ammunition |

The weapons of armor mods included in an armor and of child gear are created into lists that are thrown away; the plugins of a matrix program are created with `null` lists. The library already holds the character's other items with `ICharacter` and `ITreeNodeView`, reaches the application through `ApplicationHost.Current`, and the parity workflow treats `Chummer/` and `Core/` as the compiled source.

## Goals / Non-Goals

**Goals:**
- Armor, cyberware and gear in the library, unchanged in what they do, save, load and print.
- The app behaving and looking exactly as before, including the tree nodes of created and copied items and the weapons they grant.
- Every type defined once across the executable and the library; no call site of a `Create` or `Copy` method changes.

**Non-Goals:**
- Moving weapons, vehicles, lifestyles, `Equipment` or `StackedFocus`.
- Changing the moved code beyond what reaching the application through interfaces requires: no renames, no cleanup of their logic, no removal of parameters that are only passed on.
- Touching the canonical `bin/ChummerGenSR4.exe`.

## Decisions

1. **Separate the groups in the app first.** The three groups are about half of `clsEquipment.cs`, so moving the file could not be a rename. They are first cut out unchanged, each into a file of its own in the app (`Chummer/Armor.cs`, `Chummer/Cyberware.cs`, `Chummer/Gear.cs`) with the file's `using` lines, so that the later move of each file is a pure rename and the weapons, vehicles and lifestyles keep the history of `clsEquipment.cs`. `git log --follow` of a moved file reaches the commit that separated it; `git blame -C` finds the lines in `clsEquipment.cs`.
2. **The character interface grows by what the equipment reads.** `ICharacter` adds `Metatype`, `CHA`, `INT`, `LOG` and `WIL`, which `Character` already has publicly; the other members the equipment reads are there already. Fields, constructors and `Create` parameters become `ICharacter`; every caller passes a `Character`.
3. **The tree node view grows by child nodes.** `ITreeNodeView` adds `NewNode()`, `Add(child)` and `Expand()`. An item creates every node it used to create with `new TreeNode()` through `NewNode()` of its own node, at the same point, and adds it with `Add` where it called `Nodes.Add`, so the nodes are created, filled, added and expanded in the same order. `TreeNodeView.NewNode()` wraps a new `TreeNode`, `Add` casts the child to `TreeNodeView` and adds its node (an `InvalidCastException` for a foreign view), `Expand` expands the node; `TreeNodeView.Node` exposes the wrapped node to the app. A `NewNode` on the item's node, rather than a node factory on the host, keeps the nodes of one tree of one kind.
4. **A host for the equipment's windows and weapons.** `IEquipmentHost`, registered as `IApplicationHost.Equipment`, has `SelectNumber(min, max, description)`, `SelectWeaponCategory(description, onlyCategory)` and `CreateWeapon(xmlWeapon, character, node)`. The app's `WinFormsEquipmentHost` holds the former window code unchanged (the number window without cancel, its `SelectedValue`; the category window limited unless the forced value is `""`, its `SelectedCategory` whatever the result) and creates `new Weapon(character)` with `Create(xml, character, node, null, null, null)` in `WinFormsEquipmentHost.CreateGrantedWeapon`, which `CreateWeapon` calls after it has taken the app's `Character` and `TreeNodeView` out of the interfaces' arguments. That check is `AppArguments.Require<T>`, which returns the argument as the app's type and throws an `ArgumentException` that names the parameter, what the adapter needs and the type it got (or `null`), as the improvement dialogs do; it is a small static helper of its own, so that the unit tests can run it without the windows. The app's creation of a quality's granted weapons calls `CreateGrantedWeapon` too, so one piece of code creates every weapon that an item or a quality grants. Weapons are created through the host, not through the caller's function, because an armor creates its included mods and a gear its children with weapons that are kept nowhere, so the library needs a way to create a weapon without lists. `IEquipmentWeapon` (identifier, name, display name, `SetRange`) is what the items read and change of a weapon; the app's `Weapon` implements it with its existing members.
5. **Adding a granted weapon through a function.** Each `Create` and `Copy` that took the two lists takes an `Action<IEquipmentWeapon, ITreeNodeView>`, which the item calls where it added the node and the weapon to the lists. Where the lists were thrown away the item passes a function that keeps nothing, and where they were `null` it passes `null`, which fails when a weapon is added, as before. The app's `GrantedWeaponLists.Add(weapons, nodes)` builds the function from the caller's lists: it adds the node, then the weapon, at once, so a caller's list that the item or an improvement reads while it is created sees the same content as before. `Copy` keeps passing the function to the children's copies, as it passed the lists.
6. **The included mods' context menu through a node function.** `Armor.Create` takes a `Func<ITreeNodeView>` instead of the `ContextMenuStrip`; the app's function, `ArmorModNodes.Create(menu)`, creates a new `TreeNode` with the armor mods' context menu on each call and returns it as a `TreeNodeView`. The menu is now set when the node is created instead of after the mod fills it, which no one can see, since the node is in no tree until the armor adds it.
7. **The former signatures as extension methods.** `EquipmentTreeNodeCreation` holds the nine former `Create` and `Copy` signatures of `ArmorMod`, `Armor`, `Cyberware`, `Gear`, `Commlink` and `OperatingSystem` with `TreeNode`, `Character`, the weapon lists and the context menu. Each wraps the node in a `TreeNodeView`, or passes `null` for a `null` node, so that an item reaches a missing node as it did, builds the weapon function from the lists and calls the item's method. A call with a `TreeNode` finds no applicable instance method and binds to an extension; between the `Commlink` and `Gear` extensions, overload resolution picks the same method as it picked between the instance methods before, since the receiver and argument types are the same.
8. **Move order.** Each step builds and keeps the app's behaviour, and each is a commit of its own:
   1. the three groups of `clsEquipment.cs` cut out into their three files in the app;
   2. the interface members and the new interfaces in the library, their implementations in the app (`TreeNodeView`, `Weapon`, `WinFormsEquipmentHost` registered by `WinFormsApplicationHost`, and `AppArguments`), and the test doubles that implement them;
   3. in place, in the three files: the character, the tree nodes, the windows and the weapons only through the interfaces, the Windows Forms and drawing `using` lines removed; `GrantedWeaponLists`, `ArmorModNodes` and `EquipmentTreeNodeCreation` added, and the quality's weapon creation moved onto `CreateGrantedWeapon`;
   4. `Chummer/Armor.cs`, `Chummer/Cyberware.cs` and `Chummer/Gear.cs` moved unchanged to `Core/`.
   The moved files keep their BOM and CRLF line endings; new files are stored with CRLF like the other source files.

## Risks / Trade-offs

- **A tree filled differently.** An armor's mods and gear, a cyberware's subsystems or a gear's children and plugins in another order, colour or expansion would show differently. Mitigation: every node is created, filled, added and expanded at the same point as before, with only the node's type changed; a unit test copies gear with children of all three types into a recording node, and another checks the app view's new nodes, adding and expanding on Windows Forms nodes.
- **Granted weapons in the wrong lists.** Mitigation: the function adds to the caller's lists in the same order and at the same moment as before, the thrown-away and `null` lists keep their behaviour, and unit tests check the order, the `null` failure and the casts.
- **No case creates an item.** The capture cases open saved characters, so no `Create` method, extension, window or weapon creation of the equipment runs live, while loading, saving and the tree of loaded equipment do. Mitigation: the extensions are reviewed as wrappers of the former signatures, the build proves that no call site changed, and the adapters (the tree node view, the weapon lists' function, the mod node function, the argument checks of the host) are tested; the extensions and `WinFormsEquipmentHost` themselves name `Character` and `Weapon` and cannot be compiled into the test project, and creating equipment needs the host, the data files and the options, so they remain unverified beyond review.
- **Most of the equipment needs the host.** Display names with a rating or extra, costs, availabilities and prints read the language and the options, whose static constructors read the application host, so the unit tests cover only what runs without it: copying gear into a tree and the character view of gear. The rest is covered by the live run.

## Verification

Fixture-tested (no desktop): the candidate build at each step; a listing of the types of the executable and the library compared with a build of the source before this change; the rename similarity of the move commit; the C# tests of the moved gear with a test character and of the app's adapters.

Only a live run proves that the app starts, opens every case's character with its armor, cyberware and gear, and draws every captured window as the canonical executable does: `npm start` over the whole case suite with diagnosis, repair and widening, recording the canonical SHA-256 before and after, execution outcomes apart from visual results, and the loop's outcome for any discrepancy.
