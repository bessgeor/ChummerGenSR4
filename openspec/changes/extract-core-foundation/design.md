# Design

## Context

The app is one SDK-style net481 Windows Forms project, `Chummer/Chummer.csproj`, built by Visual Studio's MSBuild. Candidate builds go through `parity/scripts/build-candidate.mjs`, which overrides the output and intermediate folders so nothing is written into `bin/` or the source; diagnosis, repair and widening run the same script on source copies with `--source`.

Four source files hold the classes this change moves, and they depend on each other and on Windows Forms as follows:

| File | Types | Uses from Windows Forms | Uses from the other files |
|---|---|---|---|
| `clsListItems.cs` | `ListItem`, `SortListItem`, `SortByName`, `SortByDate`, `ListViewColumnSorter` | `TreeNode`, `ListViewItem`, `SortOrder` (the last three sorters only) | none |
| `clsXmlManager.cs` | `XmlManager` | `Application.StartupPath` | `LanguageManager`, `GlobalOptions` |
| `clsLanguageManager.cs` | `LanguageManager` | `Application.StartupPath`, `Application.Exit`, `MessageBox`, every control type it translates | `XmlManager` |
| `clsOptions.cs` | `MRUChangedHandler`, `ClipboardContentType`, `SourcebookInfo`, `GlobalOptions`, `CharacterOptions` | `Application.StartupPath`, `MessageBox`, the `frmMain` type | `XmlManager`, `LanguageManager` |

`GlobalOptions` also holds the cyberware and bioware grade lists as static fields of the equipment type `GradeList` and fills them in its static constructor with `Improvement.ImprovementSource` values; nothing else in the four files uses an app type outside them. `XmlManager`, `LanguageManager` and the options reference each other, so they can only arrive in a library together. The parity workflow takes `Chummer/` as the whole compiled source: the identity a candidate build records, the snapshot's compiled identity, the repair guard, the plan validation, the widened source and the accepted branch's commits all name that one folder.

## Goals / Non-Goals

**Goals:**
- A class library that cannot use Windows Forms, holding the four files' model types with their git history.
- The app behaving and looking exactly as before: the same strings, files, registry values, message boxes and control translation.
- Every type defined once across the executable and the library.
- The workflow's diagnosis, repair and widening working on the library's source as on the app's.

**Non-Goals:**
- Changing the moved code beyond what reaching the application through interfaces requires: no renames, no new properties, no cleanup.
- A test project of the library's own, a different target framework, or other assemblies. The existing C# test project references the library for the one test of the host registration.
- Touching the canonical `bin/ChummerGenSR4.exe`.

## Decisions

1. **A net481 library with an explicit reference list.** `Core/Core.csproj` targets net481 like the app, so the registry, `XmlTextWriter` and the rest of the moved code compile as they are, and no package or facade assembly is added to the output. It sets `DisableImplicitFrameworkReferences` and references only `mscorlib`, `System`, `System.Core` and `System.Xml`: the SDK's implicit list includes `System.Drawing`, and without it a Windows Forms or drawing type in the library is a compile error rather than a review finding. The assembly is `ChummerGenSR4.Core`, so it sits beside `ChummerGenSR4.exe` without a clash; its root namespace stays `Chummer`, so no call site changes. It takes the reference assemblies from the same `Microsoft.NETFramework.ReferenceAssemblies` package as the app. The app references it with a `ProjectReference`, the solution lists it, and its default output stays its own `Core/bin/`; the app copies the DLL into its output.
2. **One intermediate folder per project.** `build-candidate.mjs` passes `BaseIntermediateOutputPath` on the command line, which MSBuild hands to the referenced library as well, and two projects restoring into one folder would overwrite each other's `project.assets.json`. The library declares the property local (`TreatAsLocalProperty`) and, when one is given, uses `<given>Core\` before the SDK's props are imported. The app keeps the given folder itself, and a build from a source copy still writes nothing into the copy.
3. **Back-reference interfaces.** The library reaches the application through two interfaces:
   - `IApplicationHost`: `StartupPath`, `ShowError(text, caption)`, `ShowInformation(text, caption)`, `AskYesNo(text, caption)`, `Exit()` and `TranslateControls(object)`. It is registered once in `ApplicationHost.Current`, the first statement of `Program.Main`, before any library class is touched. Reading `ApplicationHost.Current` before a registration throws `InvalidOperationException`, and so does a second registration (the classes read the host's paths in static constructors, so a host that changed would leave part of their state built from the first); there is no default host, so a missing registration cannot pass unnoticed. `LanguageManager` reads the host before the `try` block that reports a missing default language file, so that block cannot swallow the missing registration. The moved classes are singletons with static constructors and are reached from hundreds of call sites, so a registered host keeps every call site as it is, where constructor injection would change them all.
   - `IMainForm`: `LoadCharacter` with the main window's signature; the defaults of the optional arguments are declared on the interface only, and `frmMain.LoadCharacter` takes all four arguments, because C# binds defaults from the static type and two copies could drift apart. `GlobalOptions.MainForm` becomes an `IMainForm`; `frmMain` implements it and still registers itself, and the controls and forms that open characters through it call the same method.
   The app's host, `WinFormsApplicationHost`, returns `Application.StartupPath` and shows `MessageBox` dialogs with the buttons and icons the moved code used (`OK` with `Error` or `Information`, `YesNo` with `Question`), and its `Exit` calls `Application.Exit`.
4. **Control translation stays in the app, unchanged.** `LanguageManager.Load(language, object)` keeps its signature and its order: it loads the language once, then hands the object to `IApplicationHost.TranslateControls`. The app's `ControlTranslator` holds the former `UpdateForm`, `UpdateUserControl` and `UpdateControls` bodies as they were, looks strings up through `LanguageManager.Instance.GetString`, translates only a `Form` or `UserControl` (any other object, such as the character options or null, is left alone as before), and reads the `/debug` argument that makes a missing string throw. The early return after a language file that cannot be loaded still skips the translation.
5. **List items without duplicates.** `ListItem` and `SortListItem` (which compares list items by name) move. `SortByName`, `SortByDate` and `ListViewColumnSorter` compare Windows Forms tree nodes and list view items, so they stay in the app, in `Chummer/Sorters.cs`, with their namespace and code unchanged. No type is defined in both assemblies, and the app holds no copy or wrapper of a moved type.
6. **The grade lists go to their type.** `GlobalOptions.CyberwareGrades` and `BiowareGrades` are lists of an equipment type, filled from `cyberware.xml` and `bioware.xml`, and have nothing to do with options; a library holding them would need the equipment and the improvements. They become `GradeList.CyberwareGrades` and `GradeList.BiowareGrades`, static fields of `GradeList` filled in its static constructor with the same two `LoadList` calls in the same order, and the sixteen places that read them name `GradeList` instead of `GlobalOptions`. A back-reference interface would have kept an equipment concept in the options for no caller's sake. The lists are now filled when `GradeList` is first used (opening a character with cyberware, the cyberware window) instead of when the options are first used at startup; both read the same merged data file through `XmlManager`, after the language is loaded, so their content is the same.
7. **Move order.** Each step builds and keeps the app's behaviour, and each move is a commit of its own whose renames git detects with at least 90% similarity:
   1. the library with the two interfaces and the host holder, the app's host and its registration, and `frmMain` implementing `IMainForm`;
   2. the workflow's compiled source covering `Core/`, so that any regression of the moves can be diagnosed and repaired in the library;
   3. the sorters out of `clsListItems.cs` into `Chummer/Sorters.cs`, then `clsListItems.cs` moved to `Core/ListItems.cs`;
   4. in place, still in `Chummer/`: `LanguageManager`, `XmlManager` and the options reach the application only through the interfaces, and the control translation moves into `ControlTranslator`; then the grade lists move onto `GradeList`;
   5. `clsLanguageManager.cs`, `clsXmlManager.cs` and `clsOptions.cs` moved together to `Core/LanguageManager.cs`, `Core/XmlManager.cs` and `Core/Options.cs`, since they reference each other; the move commit only drops their `using System.Windows.Forms;` lines.
   Preparing in place first keeps the move commits nearly pure renames: the control translation alone is a third of `clsLanguageManager.cs`, and moving it out in the same commit would bring the file below the similarity threshold. The moved files keep their line endings, so the renames are not hidden behind whitespace changes, and the files this change adds are stored with CRLF like the other source files, so that a checkout without line-ending conversion builds the same bytes.
8. **The compiled source is `Chummer/` and `Core/`.** One workflow constant lists the compiled folders. The snapshot copies them with `bin/data` and `bin/lang`; the compiled identity a build records and diagnosis checks covers both; the patch guard and the plan validation accept paths under either; the widened source copies both from the accepted source; and the accepted branch stages both in its source and fix commits. A source copy without `Core/` cannot be built, since the app references the library, so a widened or accepted source without it is a setup error rather than something to build and blame on the patch. The diagnosis prompts name only the compiled folders the snapshot holds, so a snapshot taken before the library existed (such as a frozen evaluation dataset) is described as it is.
9. **New prompt versions.** The diagnosis and repair prompts describe the source folders and say which may change, so their text changes, and each changed prompt gets a new version: `hypothesis-v2` (with priors `hypothesis-v2+priors-v1`), `challenge-v2`, `repair-v3`, `repair-plan-v2` and `repair-task-v2`. Eval runs and certificates are keyed on these versions, so earlier measurements are not mistaken for the new prompts; the grade prompt does not describe the source and keeps its version.

## Risks / Trade-offs

- **Behaviour hidden in the move.** A message box, path or translation that differs would change what the user sees. Mitigation: the moved code changes only at the calls to Windows Forms, each replaced by a host method that makes the same call, and the live run captures every case's windows; the control translation of every form is visible in the captures, since English captions are looked up from their tags too.
- **Static initialisation order.** A library class touched before the host is registered would throw from its static constructor. Mitigation: the registration is the first statement of `Main`; the exception names the missing registration instead of falling back to a default, and a test in the C# test project reads the host and `LanguageManager.Instance` unregistered, then registers a host and registers a second.
- **Designer support.** Visual Studio's form designer runs form constructors without `Main`, so a form that translates itself in its constructor now throws in the designer. The designer is not part of any build or check here.
- **A second assembly to stage.** A candidate copied without the DLL would not start. The capture runner already copies every file of the candidate's folder.

## Verification

Fixture-tested (no desktop): the candidate build from the repository and from a source copy outside it; a listing of the types of the executable and the library compared with a build of the source before this change; the library's assembly references; the rename similarity of each move commit; the workflow's unit tests for the compiled folders, guard, widened source, accepted branch and prompt versions; and the C# test of the host registration.

Only a live run proves that the app starts, loads its data and language, translates its forms and draws every captured window as the canonical executable does: `npm start` over the whole case suite with diagnosis, repair and widening, recording the canonical SHA-256 before and after, execution outcomes apart from visual results, and the loop's outcome for any discrepancy.
